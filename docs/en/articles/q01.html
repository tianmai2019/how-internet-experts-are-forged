🎯 Layer 1 · The User's View

Why does a page appear when you type in a URL?

A story about how the "miracle" actually happens

🤔 The ordinary user's view: why does this question matter?

We type in URLs every day — but have you ever stopped and wondered: how does this actually happen?

You type google.com, hit enter, and in less than a second, the page shows up. It looks like magic.

But behind the "magic" — dozens of systems, thousands of kilometers of fiber, hundreds of millions of computations, all working together. Understanding this process is the first step to cracking open the internet's black box.

Why is this question the starting point for Layer 1?
Because it's the curiosity every single person on the internet has. Start here, and we can peel the whole internet back, layer by layer.

🧩 Break it down: turn one big question into small ones

To answer "how does a URL become a page," we first need to answer a few smaller questions:

  1. What is a URL? What does google.com actually mean?
  2. How does the computer find that website? Where is the server?
  3. How does the request go out? How does data travel thousands of kilometers?
  4. How does the page come back? How does HTML turn into what you see on screen?

🎯 Look at it layer by layer

The user's layer: just the result

In an ordinary user's eyes, it looks like this:

Type the URL
↓
Hit enter
↓
🎉 Page appears!

That's it.
You don't need to know what happens in between — as long as it works. That's where most of us live, every day.

🔨 The build layer: starting to see the structure

The moment you start learning to code, the black box starts to become transparent. You realize — behind the scenes, it actually looks like this:

  1. 📝
    URL parsing protocol / domain / path ~a few ms
  2. 📖
    DNS lookup domain → IP address ~tens of ms
  3. 📤
    HTTP request ask the server for stuff ~hundreds of ms
  4. 📥
    Response comes back HTML / CSS / JS depends on network
  5. 🎨
    Browser rendering paint it to the screen ~tens of ms

Figure 1: the 5 core stages of a page load — the bottom labels are rough orders of magnitude

Let's walk through them one at a time:

1. URL parsing: what is a URL, really?

https://www.google.com/search?q=hello

  • https:// — the protocol (how we're going to talk)
  • www.google.com — the domain (who we're talking to)
  • /search — the path (what to look up)
  • ?q=hello — the parameters (what we're saying)

2. DNS lookup: how does a domain become an IP address?
It's like flipping through a phone book — you remember the name, but you need the number.

google.com → DNS lookup → 142.250.71.14
(name) (phone book) (phone number)

3. Sending the HTTP request: making the call
The browser has the IP address — it's like dialing the number. Then the conversation starts:

Browser: "Hi, I'd like the homepage!"
Server: "Got it — sending it now!"
Browser: "Thanks!"

4. Receiving the HTML: getting the page content
The server doesn't send back an image — it sends a chunk of HTML code, which looks roughly like this:

<html>
<head>
<title>Google</title>
</head>
<body>
<h1>Hello!</h1>
</body>
</html>

5. Rendering: turning code into a picture
The browser is a painter. It takes the HTML description and paints it, stroke by stroke, onto the canvas:

📄 Parse the HTML
🎨 Apply the CSS
⚡ Run the JavaScript
🖥️ Show it on screen

🌊 The system layer: seeing the full path

Once you get to the engineer's view, you realize this isn't just "browser talks to server." Behind the scenes, a huge distributed system is at work.

The request's journey might pass through:

1. Your phone → WiFi router → ISP network
2. CDN (content delivery network — may respond from a nearby location)
3. Load balancer (decides which server handles it)
4. Web server (handles HTTP)
5. Application server (runs the business logic)
6. Database / cache (reads the data)
7. Then all the way back the other direction!

All of this — usually done in a few hundred milliseconds. And you, sitting in front of the screen, just see the result.

⚖️ The trade-off layer: why is it designed this way?

At the senior engineer's view, you start asking: why is the system designed like this?

Every choice is a trade-off:

  • Why use domain names instead of IPs directly? → Easy to remember vs. one extra lookup
  • Why use a CDN? → Faster vs. more expensive
  • Why so many layers? → Flexible and scalable vs. more complex

✋ Try it yourself

Try this: see the process with your own eyes!

In Chrome, press F12 to open Developer Tools, switch to the Network tab, and reload the page.

You'll see every request the browser makes — and how long each one took!

Or try this:

Windows: open cmd, type ping google.com
Mac: open Terminal, type ping google.com

You'll see your computer literally talking to Google's servers!

👑 The grandmaster's view: how does this shape reality?

From technology to the world

Once you truly understand this process, the way you see the world changes.

You realize: the internet isn't "natural" — it's built by people.
Behind every design choice — business, political, and social considerations.

Think about it:

  • Why is a URL formatted this way? Who decided?
  • Why is .com so expensive? Who's making money?
  • Why can't some websites be reached from some places? Who's calling the shots?
  • Why do you get this result and not that one? Who's filtering?

That's the shift from "user" to "grandmaster": you stop just looking at the result — and start asking, "who decides this result?"

Because countless engineers built an unbelievable system, hid the complexity behind a simple interface, and let everyone enjoy the "miracle."

And now — you're starting to see the truth behind the "miracle."
