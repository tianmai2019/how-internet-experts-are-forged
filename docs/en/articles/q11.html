🔨 Layer 2 · The Beginner Coder's View

Signup, login, comment, like, order... how are these really built?

On the internet, almost every feature is old bricks rearranged

🤔 The ordinary user's take: why does this matter?

You place an order on Taobao, like a post on Weibo, comment on Xiaohongshu, log into Zhihu... on the surface, these look like five completely different features. But if I told you — they're actually the same thing underneath — would you be a little surprised?

This matters because once you spot those "underlying bricks," you'll see that what people call "a new product feature" is mostly just old bricks rearranged. That "seeing through it" ability is the dividing line between someone who uses products and someone who builds them.

Core insight:

All these features boil down to just four operations:
Create, Read, Update, Delete
Short: CRUD — plus "knowing who you are" (authentication) and "knowing what you can do" (authorization), and you can build almost the entire internet.

🎯 Peel it back, layer by layer

The user layer: only the result matters

You see it as:

  • Signup — type in a phone number, an account gets created
  • Login — enter a password, you're in
  • Comment — write some words, hit send
  • Like — tap once, it turns red
  • Order — pick an item, pay, wait for shipping

Looks like five different things. But in an engineer's eyes...

The implementation layer: seeing the structure

Translate these five features into CRUD operations, and the magic shows up:

📝 Signup

Create a row in users

INSERT INTO users(phone, password_hash) VALUES(?, ?)

🔑 Login

Read the users table + issue a token

SELECT id FROM users WHERE phone=? AND password_hash=?

💬 Comment

Create a row in comments

INSERT INTO comments(user_id, post_id, text) VALUES(?, ?, ?)

❤️ Like

Create a row in likes (unlike = Delete)

INSERT INTO likes(user_id, post_id) VALUES(?, ?)

🛒 Order

Create orders + Update inventory + Create payment...

More complex — but every step is still CRUD.

💡 Takeaway

Most internet features = combinations of CRUD + authentication + some business rules

Surprised? Let's go a little deeper — starting with how "login" actually "remembers you."

"Who are you?" — session vs. token

HTTP is a stateless protocol — every time the server gets your request, it's like it has amnesia; it doesn't know who you are. So the system needs a way to "prove who you are" on every request. Two mainstream approaches today:

🎟️ Session

After login, the server generates a session id and stores it in its own database.

You get a cookie. Every request, the browser sends the cookie, and the server looks it up.

Like a coat-check ticket — you hold the ticket, the store holds the coat.

🪪 Token (JWT)

After login, the server issues a signed string (containing "you're user_123, valid until xxx") and hands it to you.

Every request carries it, and the server just verifies the signature — no database lookup needed.

Like an ID card — you can tell if it's real just by looking.

On the frontend, after login the code usually looks like this:

// After a successful login, stash the token const res = await fetch('/api/login', { method: 'POST', body: JSON.stringify({ phone, password }) }); const { token } = await res.json(); localStorage.setItem('token', token); // Every request afterwards carries it automatically await fetch('/api/comments', { headers: { 'Authorization': `Bearer ${token}` }, method: 'POST', body: JSON.stringify({ postId: 42, text: 'Great post!' }) });

The system layer: seeing the full path

Let's zoom in on a single "order" — because it best shows how engineers combine CRUD into a "complex feature":

① Authenticate · who are you?
↓
② Validate · is the item still there?
↓
③ Decrement stock · Update inventory
↓
④ Create the order · Create orders
↓
⑤ Kick off payment · call a third party
↓
⑥ Update order status · Update
↓
⑦ Notify the merchant to ship

Here's the key point: the real difference between ordering and liking is —

Idempotency · Transactions · Consistency

Like: tapping twice equals tapping once (just dedupe) → idempotent
Order: if you tap "Pay" repeatedly, you must never be charged twice → must be strictly idempotent
Order: decrementing stock and creating the order must both succeed or both fail → transaction
Order: database, inventory, payment, merchant — four systems, and their data must eventually line up → consistency

So one "order" endpoint can be dozens or even hundreds of lines of code, carefully handling every failure mode. But at its core, it's still a few CRUD operations glued together.

The trade-off layer: why design it this way?

You might ask: if it's all the same underneath, why is every feature still so much work to build?

Because the devil's in the details — for each specific feature, engineers have to think about very different things:

  • Like: think about "high concurrency" — a trending Weibo post gets tens of thousands of likes a second; can the database handle it? Usually you need a counter cache and async writes.
  • Comment: think about "content safety" — spam floods, abuse, ads. You need keyword filtering and rate limiting.
  • Login: think about "account security" — passwords can't be stored in plain text (hash + salt), you have to defend against brute-force attacks and credential stuffing, and maybe throw in SMS codes or CAPTCHAs.
  • Order: think about "correctness of money" — overselling stock, double charges, mangled orders are all disasters, and everything needs a rollback plan.
So a programmer's real skill isn't writing CRUD — anyone can write CRUD.
The skill is knowing "what else this specific situation needs you to think about."

That's why "a newbie writing an order endpoint" and "a senior engineer writing an order endpoint" can differ by 10x in lines of code — the senior thought through 10x more failure modes.

✋ Try it yourself

Try this: spot the "CRUD pattern" in an app you already use

Open any app (WeChat, Douyin, Bilibili...), pick a feature you use all the time, and try to answer:

  • Which table does it hit? (users? posts? follows?)
  • Is it Create, Read, Update, or Delete?
  • Does it need authentication?
  • Does it need to be idempotent?

For example:

  • Follow someone = Create a follows row (user_id, target_id)
  • Unfollow = Delete that same row
  • Scrolling the recommendation feed = Read with complex ranking + pagination
  • Posting to Moments = Create a moments row

Do this exercise a few times and you'll start to feel like you can "see through" apps.

👑 The Grandmaster's View: how does this shape reality?

A product's "new features" are mostly old bricks rearranged

You hear "app X just launched a new feature," and it sounds cool and innovative — but from an engineer's angle, most so-called "new features" are just existing primitives reassembled:

• Weibo's "retweet" = a special kind of Create
• Douyin's "favorite" = Create + Delete, similar to like
• Taobao's "cart" = a per-user temporary Create, batched into orders on checkout
• WeChat's "Moments" = Create post + complex visibility (authorization) rules
• Pinduoduo's "help me chop the price" = Create + state machine + notifications

Real innovation isn't in the bricks themselves — it's in how they're combined.

That's why great product managers and engineers always ask first: "Can we build this out of what we already have?" — because assembly is far cheaper than invention.

Once you can recognize the assembly patterns, you jump from "user" to "designer." You'll see that behind every popular product is a careful choreography of "CRUD + authentication + business rules."

That's the secret of the internet world: it's much simpler than it looks, and much more clever than it looks.

✨ Back to the question

So — signup, login, comment, like, order... how are they really built?

They're almost all combinations of CRUD (Create, Read, Update, Delete) + authentication (who you are) + authorization (what you can do). It's just that features like ordering — where money and state are involved — need extra guardrails: idempotency, transactions, consistency.

Once you have this "list of bricks," you'll find — no matter how complex a product looks, break it open and it's the same foundational blocks assembled together. That "see through it all" ability is the first ticket into the world of people who build products.
