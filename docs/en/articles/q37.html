Why does org structure end up shaping system architecture?

Conway's Law: the architecture diagram you draw ends up looking like your org chart

🤔 The Ordinary User's View: why does this matter?

You've probably noticed something odd — a lot of big-company products feel like features stitched together. Why do Taobao and Alipay look so similar but stay separate? Why do different tabs inside the same app have wildly different design styles?

You might blame "the designers weren't consistent" or "the PM had no taste." But there's an iron rule behind it:

Conway's Law (1968):

"Any organization that designs a system will inevitably produce a design whose structure mirrors the organization's communication structure."

→ 3 teams building a browser produce a browser made of 3 stitched-together modules.
→ 1 team building it produces a monolith.

In plain English: your code looks like your org. This is the most invisible — and most unstoppable — force in software engineering.

🎯 Peel it back, layer by layer

The User's View: they only see the result

A user says: "Some parts of this app are great, other parts feel really disjointed." "Logging in takes three screens." "The search results and the shopping cart look like they were built by totally different teams."

Those "disjointed" feelings are almost always the projection of an org wall.

The Beginner Coder's View: starting to see the shape

Say 3 teams are collaborating on one app:

// Each team's boundary Team A: user module → one UserService Team B: product module → one ProductService Team C: payment module → one PaymentService // Result: the architecture naturally splits three ways // Because cross-team communication has a cost, API boundaries always land on team boundaries // What if Team A and Team B don't get along? // —— A "translation layer" shows up to decouple them // —— That translation layer is the interpersonal relationship, made real in code

This isn't theory — it happens every day. Three people on your team stop talking, and one extra middle layer appears in the code.

The Engineer's View: the full path

Amazon is the company that used this law in reverse most successfully. Look at the path:

Jeff Bezos's "two-pizza team" rule (2002) ↓ Every team small enough to be fed by two pizzas (6–10 people) ↓ Every team independent, with its own KPIs and API boundaries ↓ Teams must talk through APIs — no "bypassing the API" allowed ↓ The org took the shape of microservices ↓ The system architecture naturally became a microservices architecture ↓ Those internal APIs eventually became AWS

This is the Inverse Conway Maneuver: if you want a certain system architecture, first reshape the org into that shape.

The Senior Engineer's View: why design it this way?

Are microservices good? Are big monoliths bad? Not necessarily — each choice matches a different organizational reality:

Monolith

Good for small teams (< 30 people). Everyone shares one codebase — low communication cost, fast iteration.

Microservices

Good for big organizations. Each team is autonomous, and APIs isolate communication complexity — but you pay for it in ops and consistency.

Modular Monolith

The in-between. Code lives together physically, but layered logically. Fits teams that "want microservices but the org isn't there yet."

Distributed Monolith

The worst of the bunch. Looks like microservices, but the coupling is still there. Usually the result of "changing the architecture before changing the org."

The first question in any architecture choice is never "which is technically better" — it's "what does my org look like?"

✋ Try it yourself

🔍 Observation exercise: draw "org chart vs system architecture"

Pick a product you know well (Taobao, WeChat, Douyin, whatever) and try to answer:

  1. Draw its main modules (recommendations, search, chat, payment, live streaming…);
  2. Guess how many teams sit behind each module;
  3. Notice which modules "flow smoothly together" (probably one BU)?
  4. Notice which modules "feel awkwardly bolted on" (probably different BUs stitched together)?

If you've worked at a company, look back at your product — you'll find every awkward seam matches an org wall.

👑 The Grandmaster's View: how this shapes reality

System architecture = the org chart, projected into code

The deeper meaning of Conway's Law: software isn't "designed" — it's "grown." It grows along the shape of the organization, along human communication paths, along power relationships.

This explains a lot of "tech mysteries":

  • Why do Google's products keep launching and getting killed? — because the org keeps reorganizing;
  • Why does the tech stack of a big company always fracture? — because different BUs pick tech independently;
  • Why do open-source projects often evolve into "a federation of small modules"? — because contributors are distributed;
  • Why do startup apps feel more "coherent"? — small team, dense communication, few boundaries.

What the grandmaster sees one layer deeper: technical architecture and social structure are two sides of the same thing. How you organize people is how you organize information — and how you organize information decides what shape the system can grow into.

That's why the truly great CTOs are also great organization designers.
The person fixing code is really fixing the relationships between people.

✨ Back to the question

So — why does org structure end up shaping system architecture?

The answer: because software is written by people, and the communication structure of those people decides the coupling structure of the code. You can't draw a beautiful architecture diagram and expect it to magically "come true" inside a messy org — it will end up looking like the org actually is.

The grandmaster's awakening:

Next time you see an "ugly system," don't blame the engineers first.
Ask instead: what does the org building this system look like?
The answer is usually right there.
