🌊 Layer 3 · The Engineer's View

What actually happens when you type a URL?

From one button to a full request path

🤔 The ordinary user's angle: why does this question matter?

You've probably heard the classic interview question: "What happens after you type google.com into a browser?"

Why does this question matter so much? Because it's not testing recall — it's testing this:

Can you see the world as something that flows?

What an ordinary user sees:
Click → page appears

What an engineer sees:
Data moving, requests being passed, systems working together

That's the heart of Layer 3 — going from "seeing things" to "seeing flow."

🧩 Break it down: turn the big question into small ones

The whole thing splits into a few steps:

  1. Find: Where is this site? (DNS)
  2. Connect: How do we reach it? (TCP/TLS)
  3. Request: What do I want? (HTTP)
  4. Process: How does the server work? (backend)
  5. Return: How does the content come back? (response)
  6. Display: How does the browser paint it? (rendering)

🌊 Peel it back, layer by layer

The user layer: only the result

To an ordinary user, this all happens in an instant:

🔤 Type the URL
↓
⚡ Hit Enter!
↓
🎉 Page appears!

Simple. Nice. But that's not the truth.

The implementation layer: you start seeing the process

To a beginner coder, it turns into "request-response":

Browser asks: "Hi, give me the homepage!"

Server answers: "Sure, here's the HTML!"

But that's still just the tip of the iceberg. The real world is a lot messier.

The system layer: the full 8-step journey!

Now let's step into the engineer's view and look at what happens millisecond by millisecond:

1 📍 DNS lookup: find where the server is

The browser first asks: "What's the IP address of google.com?" It's like checking a contact list — using a name to find a phone number.

And it's not one question — it might ask the local cache, the router, the ISP, all the way up to the root DNS servers — one hop at a time.

2 🔌 TCP handshake: open the connection

Once it has the IP, the browser starts the "three-way handshake" with the server:

"SYN!" → "SYN-ACK!" → "ACK!"
Like a phone call: "Hello?" "Yeah?" "OK let's talk"

3 🔐 TLS handshake: encrypt the channel

If it's HTTPS, this is where the two sides negotiate the encryption and exchange keys. That's where the little padlock icon comes from!

4 📤 HTTP request: state the ask

The browser finally gets to the point:

GET / HTTP/1.1
Host: google.com
User-Agent: Chrome/120.0
Accept: text/html

5 🏭 Server processing: the journey inside

Once the request lands on the server, the real story begins. It travels through an entire infrastructure chain:

  1. 👤
    UserThe browser fires the request
  2. 🚀
    CDN cacheOn hit, static assets return directly
  3. ⚖️
    Load balancerRoutes to the least-busy machine
  4. 🖥️
    Web clusterNginx / reverse proxy
  5. 🧩
    App serviceRuns business logic
  6. ⚡
    Cache (checked first)Redis · millisecond-level
  7. 🗄️
    Database (fallback on miss)MySQL / PostgreSQL

A typical topology of one request crossing the infrastructure — cache hit returns immediately, only a miss falls through to the database

The request might pass through several services, hit several databases, and only then does the data get assembled.

6 📥 HTTP response: the content comes back

The server sends the HTML, CSS, and JS back:

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234

<!DOCTYPE html>...

7 🔄 More requests: fetch the assets

The HTML is only the start! The browser sees it also needs CSS, JS, images... so it fires off more requests, loading in parallel.

8 🎨 Render: the page appears!

The browser parses the HTML, applies CSS, runs JS, and paints the pixels. And finally — you see the page!

And all of this usually happens in a few hundred milliseconds!

This is Layer 3 waking up:

The internet isn't a "teleporter" — it's a precise system,
built out of countless tiny steps, and every single one matters!

The trade-off layer: why is it designed this way?

You might ask: why so many steps? Can't we just simplify it?

That's the engineer's mindset — every choice has a cost:

🔀
DNS resolution

Memorable but slow

🔒
TLS encryption

Secure but slow

⚡
CDN cache

Fast but costs money

📊
Load balancing

Stable but complex

Add all of these up, and you get the modern web: a system full of trade-offs.

✋ Try it yourself

Watch the request journey with your own eyes!

In Chrome:

  1. Press F12 to open DevTools
  2. Pick the Network tab
  3. Refresh the page
  4. You'll see every single request!

Click any request and you get the detailed timeline: how long DNS took, how long the connection took, how long the download took...

Want to go a little deeper? Try this command:

traceroute google.com

You'll see where your packets go, and how long each hop takes!

👑 The Grandmaster's View: how does this shape reality?

From flows of data to flows of power

Once you understand the path data takes, you start to see:

Whoever controls the path controls the information.

Think about these:

  • Why can't some sites be reached from certain places? Because a segment of the path is cut off.
  • Why does the CDN matter so much? Because it puts content closer to you — and also controls how content is delivered.
  • Why do big companies build their own data centers? Because whoever owns the infrastructure owns their destiny.
  • Why is privacy so hard? Because your request passes through too many hands, and every one of them can log it.

That's the Grandmaster's View: seeing the tech, and also the power, economics, and politics behind the tech.
