What is a database actually storing?

The world has to be modeled as tables before a system can "see" it

🤔 The ordinary user's angle: why does this matter?

Your Alipay balance, your WeChat friends, every item you've ever bought on Taobao, that Moment you posted on March 12 last year — they all live somewhere. That somewhere is called a "database."

But what does a database actually look like? Is it a giant file? A pile of Excel spreadsheets? More importantly: what can be stored in one, and what can't?

Core insight:

A database doesn't store "reality" — it stores reality that has been modeled.
You have to decide first: what attributes does this thing have, how does it relate to other things?
Only then can you fit it into a database.

Whatever hasn't been modeled — the system can't see.

This question matters not because you need to learn SQL — but because once you understand "how a database sees the world," you understand why product managers argue every day about "should we add this field?" and "are these two things really the same category?"

🎯 Peel it back, layer by layer

The user layer: only the result matters

You open Meituan and see the order you placed last month — "Empress Milk-Cap Matcha, add taro balls, no sugar." You feel like Meituan "remembers" what you bought.

But how does Meituan "remember"? It doesn't have memory like a human — it has a table called orders, and there's a row in it that looks roughly like this:

order_id | user_id | shop_id | items | price | status | created_at ---------+---------+---------+--------------------------------+-------+---------+--------------------- 9382174 | 8827 | 501 | Empress Milk-Cap Matcha (taro, no sugar) | 22.5 | done | 2024-05-13 14:22:41

That row is how your bubble tea gets "remembered" by the database. It's not a copy of your memory — it's a formatted fact.

The implementation layer: starting to see the structure

The most common kind of database is called a relational database (MySQL, PostgreSQL, SQL Server…). It describes the world as a bunch of "tables," and each table has rows and columns:

What tables does the simplest blog system need?
-- users table: one row per user CREATE TABLE users ( id BIGINT PRIMARY KEY, phone VARCHAR(20) UNIQUE, nickname VARCHAR(50), created_at TIMESTAMP ); -- posts table: one row per post CREATE TABLE posts ( id BIGINT PRIMARY KEY, author_id BIGINT REFERENCES users(id), -- who wrote it title VARCHAR(200), content TEXT, created_at TIMESTAMP ); -- comments table: one row per comment CREATE TABLE comments ( id BIGINT PRIMARY KEY, post_id BIGINT REFERENCES posts(id), -- on which post user_id BIGINT REFERENCES users(id), -- who commented text TEXT, created_at TIMESTAMP );

Notice those REFERENCES — that's the heart of "relational." Every row in the comments table points, via post_id and user_id, to a specific row in two other tables. That's why it's called "relational" — tables have relationships with each other.

Once you have tables, you can "ask questions":

-- Find every post user 8827 wrote yesterday SELECT id, title, created_at FROM posts WHERE author_id = 8827 AND created_at >= '2024-05-12' AND created_at < '2024-05-13'; -- Find every comment on this post, including the commenter's nickname SELECT c.text, u.nickname, c.created_at FROM comments c JOIN users u ON u.id = c.user_id WHERE c.post_id = 42 ORDER BY c.created_at DESC;

SQL is "the language you use to talk to the database." It reads like English, and it's written as "what I want," not "how you find it."

The system layer: seeing the full path

If a database were just "storing tables," decades of research wouldn't have much to chew on. The hard part is balancing "fast, correct, reliable". For that, it introduces a few key concepts:

📇 Index

Like the index in a book. Without one, finding a word means flipping through every page. With one, you jump straight to it.

The cost: the index takes space, and every write has to update the index too.

🔒 Transaction

A group of operations that must all succeed, or all fail.

In a money transfer, "subtract 100 from my account" and "add 100 to the other account" must live or die together — otherwise money vanishes or appears from nowhere.

📐 Schema

The database's "design blueprint" — how many tables, what fields each has, what types those fields are.

When a product iterates, adding fields or changing types is called a "schema change" — get it wrong and things go down.

♻️ ACID of transactions

Atomicity, Consistency, Isolation, Durability — the safety guarantees a database provides for "money" and "accounts."

One database read/write — what happens behind the scenes?
① SQL arrives
↓ parse + optimize
② generate execution plan
↓ decide which index to use
③ read disk / memory pages
↓ assemble result
④ return to the app

A database doesn't "walk through every byte on disk" — it maintains a carefully designed set of B+ trees, hash tables, log files, so that "looking up one row" usually takes just a few disk I/Os and completes in milliseconds.

The trade-off layer: relational vs NoSQL — why the split?

For decades relational databases ruled the world, but around 2010 a wave of "rebels" showed up — MongoDB, Redis, Cassandra, Elasticsearch… Collectively they're called NoSQL (Not Only SQL).

🏛️ Relational (MySQL, PostgreSQL)

Rigorous structure, supports complex queries and transactions.

Fits: money, accounts, orders, user relationships — anything you "can't get wrong."

Weakness: hard to scale horizontally for massive data.

🚀 NoSQL (MongoDB, Redis, Cassandra)

Flexible shape, trades some consistency for huge gains in performance and scale.

Fits: caches, logs, social feeds, search — anything "big, fast, changing fast."

Weakness: complex transactions and cross-table queries are weaker.

Real-world large systems usually use both:

  • Your account balance, your orders — go in MySQL/PostgreSQL (must be "correct")
  • Your activity feed, your recommendations — go in Redis/MongoDB (must be "fast")
  • Your search terms, your logs — go in Elasticsearch (must be "full-text searchable")
This tells us something too:

"Database" isn't one thing — it's a whole category of tools.
An engineer's job is to pick the right combination from many databases to match the business's needs.

✋ Try it yourself

Try this: 5 minutes — write out the "data model" for a product you know

Grab a piece of paper (or any notes app), and think of a product you know well — say WeChat or TikTok.
Then answer: if you were its engineer, what tables would you need?

Take WeChat. You might write down:

  • users: id, phone, nickname, avatar_url
  • friends: user_id, friend_id, added_at (who's friends with whom)
  • chats: id, type (1-on-1 / group), created_at
  • messages: id, chat_id, sender_id, content, sent_at
  • moments: id, user_id, text, images, posted_at

Do the exercise and you'll notice a strange feeling:
an app, really, is just a collection of tables.

👑 The Grandmaster's View: how does this shape reality?

Only a world that can be expressed in a database gets "seen" by the system

Here's a truth that's easy to miss:

If something can't be modeled as "tables and fields," an internet system can't process it.

Your gender is "male / female"? — because the first table had a gender field with exactly two enum values. Today many platforms add "other," "prefer not to say," "non-binary" — that's not because society suddenly progressed, it's because the database schema got extended.

Your ID number can only be 18 digits? Your name can't be more than 20 characters? Your family relationships have to be "father / mother / son / daughter"? All these seemingly natural "rules" are, at bottom, decisions some engineer made while defining a table structure.

The database is a filter for reality. It decides what the system sees, what the system ignores, what the system forces into a category.

Every time you fill in a form in an app, you're translating "the living you" into fields a machine can understand. Your complexity gets compressed, your many sides get single-selected, your fuzziness gets enumerated — that's the cost of "digital existence."

That's also why every schema change, every "new field added," can be a quiet social conversation.

✨ Back to the question

So, what is a database actually storing?

It's not storing "the world" — it's storing "the world after engineers modeled it": rows and rows of strictly structured tables, where rows are records, columns are attributes, and relationships between tables are expressed through references.

Behind that sits an intricate machine: indexes make lookups fast, transactions guarantee consistency, schemas constrain the shape of data. Relational and NoSQL are two camps with different priorities — modern systems usually use both.

The deeper truth:

Next time you open any app, try asking yourself:
"If I were its engineer, how would I design its tables?"

The more tables you can imagine — the more of that product you understand.

And here you are — you've finished the first stretch of "The Beginner Coder's View." Congrats — you went from someone who sees the world, to someone who can see through its structure.
