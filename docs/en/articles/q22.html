Why can load balancing let one service handle a flood of requests?

The illusion that turns "one service" into "a whole army of services"

🤔 An ordinary user's view: why does this matter?

Ever stop to think about something weird — a billion people in China are all hitting the same "www.taobao.com", refreshing all day. Why doesn't that one machine drop dead? And even stranger: if it did drop dead, how come no user ever noticed?

The answer — you think you're talking to "a Taobao server", but you're actually facing an entire data center, tens of thousands of machines. The thing quietly dispatching your request to one of them is called a load balancer (LB).

What is load balancing, at its core?

One line: it makes "one service" look like a single machine, when in fact it's a crowd of them.
From the outside, a single point. Inside, an army.

Understand load balancing and you understand "horizontal scaling" — the single most important idea in internet architecture. It's why big tech can "just add machines to survive traffic" without rewriting code.

🎯 Peel it back, layer by layer

The user layer: only the result matters

An ordinary user's awareness of load balancing — zero. All they feel is:

  • How is this site so "solid"? Even on Singles' Day, with all those people, it just works.
  • Occasionally a request feels slow — refresh and it's fine (actually, you got routed to a different machine).
  • They have no clue that in a single second, "Taobao" is really thousands of machines serving different users at once.

And that's the greatest thing about load balancing — it makes complexity disappear from the user's view.

The build layer: starting to see the structure

The simplest load balancer is Round Robin: a request comes in — the first goes to machine A, the second to B, the third to C, the fourth back to A… and so on.

# A minimal "application-level" load balancer (pseudocode) servers = ["10.0.0.1", "10.0.0.2", "10.0.0.3"] counter = 0 def pick_server(): global counter server = servers[counter % len(servers)] counter += 1 return server def handle_request(req): backend = pick_server() return forward(req, backend) # forward the request over

The real world is way more complex, of course, but the spirit is identical: one "dispatcher" out front spreads requests across a pool of "workers" behind it.

The system layer: seeing the full path

In real internet systems, load balancing isn't one layer — it's a stack of layers, each nested inside the next.

【User】
↓ via domain www.taobao.com

【DNS load balancing】(returns different data-center IPs based on proximity)
↓
【L4 load balancer】(LVS / F5 — splits by IP + port, ultra fast)
↓
【L7 load balancer】(Nginx / Envoy — fine-grained routing by URL / Header)
↓
【Backend service cluster】machines A, B, C, D, E…

All along this path, every layer is "dispatching" — just at different granularities:

DNS load balancing

Coarsest granularity: returns different data-center IPs by geography.
Beijing users get the Beijing data center, Guangzhou users get Guangzhou.

L4 load balancing (transport layer)

Splits by IP + port, doesn't look at request content.
Blazing fast — a single LVS box can handle hundreds of thousands of QPS. But it can't "see the content" for smart routing.

L7 load balancing (application layer)

Can see HTTP URL, Header, Cookie.
Can do things like "route /video to the video cluster, /pay to the payment cluster".

Service Mesh

Finer still: load balances calls between services inside the system too.
Classic examples: Istio, Envoy. A must-have in the microservices era.

Besides "how to split", load balancing has one more critical weapon: health checks. Every few seconds, the LB pings each backend — "you still alive?" Dead machines get automatically kicked out of the pool, and new requests stop going there. That's the secret behind "a machine died and no user noticed".

The trade-off layer: why is it designed this way?

Load balancing looks simple, but it hides a few brain-bending trade-offs:

The core trade-off: even distribution ↔ session stickiness
Want it truly even → the same user may land on a different machine each time → login state gets lost.
Want "same user → same machine" (session sticky) → some machines end up more loaded than others.

A few classic strategies you'll eventually have to pick from:

  • Round Robin: most fair — but ignores machine performance.
  • Weighted Round Robin: stronger machines get a bigger share.
  • Least Connections: whoever has the fewest open jobs gets the next one. Good for workloads with uneven request times.
  • Consistent Hashing: the same user / same key always lands on the same machine — great for cache affinity. When you add a machine, only a small fraction of requests need to "move house".
  • IP Hash: split by client IP — a cheap way to get sticky sessions.
Common misconception: "with load balancing, nothing ever goes down".
The LB itself is a single point! If the LB dies, hundreds of machines behind it become "islands". So real systems run multiple LBs in active-standby (Keepalived + VIP, high-availability SLB clusters in the cloud), and even DNS returns several LB addresses. There's no such thing as truly no single point — only more backups.

✋ Try it yourself

See "which machine you're hitting" with your own eyes

Run this in your terminal:

$ nslookup www.baidu.com
Server: 8.8.8.8
Address: 8.8.8.8#53
Non-authoritative answer:
Name: www.a.shifen.com
Address: 110.242.68.66
Address: 110.242.68.4

See that? It returned multiple IP addresses. That's the most direct evidence of DNS load balancing — one domain, a bunch of IPs behind it. Your browser picks one to connect to; the rest are its "backups".

Try it again with curl:
curl -I https://www.taobao.com — watch the Server or Set-Cookie headers, and you may see different data-center markers.

👑 The Grandmaster's View: how does this shape reality?

Load balancing = syntactic sugar for scalability

In the era before load balancing, "getting stronger" had exactly one meaning — replace this machine with a more expensive one. That's called "vertical scaling". Expensive, with a clear ceiling, and when it fails you're back to square one overnight.

Load balancing opens up a different kind of "getting stronger" — horizontal scaling: machines not enough? Just add more. Add ten, get ten times the capacity. From that moment on, "performance" is no longer a hardware problem — it's a money and architecture problem.

Underneath, there's a grandmaster-level insight:
"One service" is a story. "A crowd of services" is the truth.

This idea reaches far beyond tech — straight into how organizations run:
· Why can a company "expand 100x without collapsing"? Because it broke "one CEO deciding everything" into "many business units deciding independently" (organizational load balancing).
· Why can a nation's administrative system cover hundreds of millions? Because it has the "central → province → city → county → township" layered dispatch (hierarchical load balancing).
· Why does a big university lecture get split across rooms? Because one room can't fit everyone (session stickiness + traffic splitting).

Every system that "stays stable under a flood of requests" — software, organizations, entire societies — is doing the same thing: turning "one entrance" into "an army".

✨ Back to the question

So — why can load balancing let one service handle a flood of requests?

Because it decouples the concept of "one service" into "a crowd of machines + one entrance". The entrance handles routing and keep-alive. The machines do the actual work. More requests? Add machines. A machine dies? Kick it out, swap in a new one. The outside world only ever sees one rock-solid "service".

What's really great about load balancing isn't how fast it is —
it's that it turns "scaling" into an addition problem.
You don't need to refactor. You just add machines.
