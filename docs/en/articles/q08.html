What are frontend and backend actually doing?

A restaurant's front-of-house and back-of-house

🤔 The ordinary user's take: why does this question matter?

You've probably heard a programmer friend say something like: "I do frontend," or "I'm a backend engineer." It sounds like two totally different jobs — but a webpage is just a webpage, right? Why does it take two separate crews to build one?

This question matters because it hides the internet's most basic division of labor: what should run on your device, and what should run on some faraway server?

Core insight:

Frontend = what you can see, touch, and run on your phone / laptop
Backend = what you can't see, running on someone else's machine, keeping the data

They talk to each other through HTTP + JSON.

Once you get this split, you'll suddenly understand: "my connection is slow, the page won't load" and "the server crashed, nobody can use it" are two completely different kinds of failure.

🧩 Peel it back: break the big question into small ones

To understand frontend and backend, you only need to ask yourself 4 questions:

  1. Who's running the code? Your browser, or a faraway machine?
  2. Who's storing the data? Where does it live, and who can change it?
  3. How do they talk? What language do frontend and backend use with each other?
  4. Why split it this way? Can't the browser just do everything?

🎯 Peel it back, layer by layer

The user layer: only the outcome matters

You open Taobao, tap "My Orders," and the page shows you the shoes you bought yesterday. In that moment, it never crosses your mind: "This order info actually flew here from a database thousands of kilometers away."

In the user's eyes, it's all just "the webpage." There is no frontend or backend — only "works" or "doesn't work."

The implementation layer: starting to see the structure

Let's use a metaphor: an internet service is like a restaurant.

🍽️ Frontend = front-of-house

The menu, the tables, the lighting, the waiter's smile. Everything the customer can see.

Responsible for: presenting the menu beautifully, taking down what the customer wants, and bringing the food to the table.

🔥 Backend = back-of-house

The pantry, the stove, the dishwasher, the ledger. Invisible to the customer — but it's what defines the real strength.

Responsible for: cooking, tallying the bill, managing stock, recording orders.

So frontend does: what the page looks like + how users can interact with it. Backend does: where data lives + how business rules get computed.

Here's a concrete example — a "like" button:

// [Frontend] Written in the browser — decides what the button looks like and how it reacts <button id="like-btn">❤️ Like</button> document.getElementById('like-btn').addEventListener('click', async () => { // Turn red — give the user instant feedback document.getElementById('like-btn').classList.add('liked'); // Quietly tell the backend: this user liked this post await fetch('/api/like', { method: 'POST', body: JSON.stringify({ postId: 42 }) }); });
# [Backend] Written on the server — decides what "like" actually means @app.post("/api/like") def like(request): user_id = get_current_user(request) # Who are you? post_id = request.json["postId"] # Which post? db.execute( # Write it to the database "INSERT INTO likes(user_id, post_id) VALUES(?, ?)", [user_id, post_id] ) return {"ok": True, "total": count_likes(post_id)}

See it clearly? The look of the button and the click-turns-red effect belong to the frontend. But "this like was actually remembered, and counted into the total" — that belongs to the backend.

The system layer: seeing the full path

Put them together, and one interaction looks like this:

👆 You tap the button
↓ (JS runs in the browser)
📦 Package a JSON request
↓ (HTTP goes over the network)
🌐 Backend endpoint receives it
↓ (Runs business logic)
💾 Reads / writes the database
↓ (Packages the result)
📨 Returns JSON
↓ (Browser parses it)
🎨 Updates the page

That invisible line between frontend and backend has a proper name — API (Application Programming Interface). It's like the restaurant's order ticket — it spells out "what to make, what to add, what to leave out." Front-of-house and back-of-house both accept the same format. Swap out any person, and it still works.

The API contract usually looks like this:

Request: POST /api/like, carrying { "postId": 42 }
Response: { "ok": true, "total": 133 }

Once this "contract" is locked, frontend and backend can each change independently — as long as both sides still honor the contract.

This is why, at big companies, frontend and backend can be two different teams — even writing in two totally different languages (JavaScript on the frontend, Java / Python / Go on the backend) — and the product still works.

The trade-off layer: why design it this way?

You might wonder: browsers are getting more powerful every year — why not just let the browser do everything? Or the other way: why not have the backend handle everything?

🚫 The problem with "all frontend"

Users can edit the code! You write "ship only after payment succeeds" — they change if (paid) to if (true), and they get it for free.

Data also can't be shared — the like you tapped on your phone won't show up on your laptop.

🚫 The problem with "all backend"

Every single click has to make a round trip to the server. Scrolling, hovering, animations… the experience gets so laggy nobody wants to use it.

And the server load would explode.

So engineers eventually settled on an unspoken agreement:

The division principle:

• Display, interaction, animation → frontend (as close to the user as possible)
• Data, rules, permissions, billing → backend (as close to trust as possible)
• Stateless APIs → so the backend can be copied and scaled at will

Note that last point: most backend endpoints are stateless — every request carries enough information on its own (like a login token), so the backend doesn't need to "remember what you said last time." That's what lets the system scale horizontally to thousands of servers — any one of them can handle your request.

✋ Try it yourself

Try this: see frontend and backend talking, with your own eyes

1. Open any webpage (Zhihu, Bilibili, whatever)
2. Press F12 to open DevTools
3. Switch to the Network tab and filter to Fetch/XHR
4. Click around, scroll, like something, leave a comment

You'll see a stream of requests appear — that's the frontend quietly having a conversation with the backend! Click into any one of them, and you can see: the JSON sent out, the JSON that came back. Right there in the open.

In that moment, you go from "webpage user" to "webpage observer."

👑 The Grandmaster's View: how does this shape reality?

The frontend / backend split is the birth of the "trust boundary"

Today we take "frontend / backend separation" as the natural order — but history didn't start there.

In the early web (the 90s), there was barely any concept of "frontend" — the server spat out a full HTML page, and the browser just displayed it. It wasn't until AJAX arrived (around 2005) that browsers could, for the first time, "talk behind the server's back." Then smartphones exploded, SPAs (single-page apps) took over, and only then did frontend truly emerge as its own discipline.

The essence of that dividing line is the boundary of trust.

Your device can be modified by you — so anything that "must be true" — your balance, your identity, whether an order has been paid — has to live somewhere you can't touch. Backend isn't just a technical choice. It's the gatekeeper of the rules.

Every time you open an app, you're agreeing to one thing: "In this world, some truths aren't mine to decide."

✨ Back to the question

So — what are frontend and backend actually doing?

Frontend handles "presentation" and "interaction" — making it something you can see, tap, and feel at home with.
Backend handles "memory" and "rules" — deciding what's true, what should happen, and who's allowed to do what.

They talk to each other through an API — like a restaurant's front-of-house and back-of-house passing order tickets. The front can change its style, its language; the back can swap chefs, swap stoves — as long as the "contract" on the ticket doesn't change, the customer always gets their plate of food.

Next thought:

When you write frontend code, you're "sculpting user experience."
When you write backend code, you're "writing the rules of the world."

Neither one can stand alone — together, they're what we call a "product."
