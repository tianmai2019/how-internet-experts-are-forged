🌊 Layer 3 · The Engineer's View

Why do some websites open fast, while others are always slow?

"Slow" isn't one cause — it's a whole request path getting exposed

🤔 The ordinary user: why does this question matter?

You've been there. Same browser, same laptop — Google and Baidu return results almost instantly, but some corporate website spins for 5 seconds. Taobao's homepage opens in a blink; some obscure shopping site makes you wait forever after one click. Why?

The reflex answer: "Their servers must suck." But is it really that simple?

"Fast" and "slow" aren't a single number — they're a whole path.

Between you hitting Enter and the first pixel showing up, dozens — sometimes hundreds — of things happen. Any one of them slows down, and all you see is "this website is slow."

Understanding "why it's slow" is really understanding "how a website is actually assembled." This is your first lesson going from The User's View to The Engineer's View.

🧩 Break the big question into smaller ones

  1. Finding the server: how long did DNS take?
  2. Establishing the connection: how long did TCP + TLS take?
  3. The request's route: how far are you from the server?
  4. Backend processing: how long did the server take to compute the answer?
  5. Resource size: how big are the HTML, JS, CSS, images, fonts?
  6. Browser rendering: once the bytes arrive, how long does painting take?

🎯 Peel it back, layer by layer

User layer: only the outcome

An ordinary user has one sensation: "fast" or "slow." They don't distinguish "DNS was slow" from "rendering was slow." They only know that if the white screen lasts more than 3 seconds, they're gone.

Google found this back in 2009: 400ms more load time = 0.6% more users lost. Amazon has estimated that every 100ms of extra latency costs 1% in sales.

Implementation layer: seeing how it's built

Open Chrome DevTools, click the Network panel, pick any request, and you'll see a Waterfall chart:

Request: https://example.com/index.html ├── Queueing 2 ms ├── DNS Lookup 35 ms ← finding the server ├── Initial connection 80 ms ← TCP three-way handshake ├── SSL 120 ms ← TLS handshake (HTTPS) ├── Request sent 1 ms ├── Waiting (TTFB) 240 ms ← server is computing └── Content Download 45 ms ← downloading HTML Total: ~523 ms

That's the "health report" for a single request. TTFB (Time To First Byte) reflects backend speed. Content Download reflects resource size and network speed. DNS / SSL reflects the cost of setting up the connection.

System layer: the full path

A real "open a website" is a relay race. Any runner drops the baton, and the whole race stalls:

User's browser ↓ ① DNS resolution (could be 5ms, could be 300ms) ↓ ② TCP + TLS handshake (across an ocean → 200ms+) ↓ ③ Request sent, through ISPs, backbones, CDN edge nodes ↓ CDN edge node (cache hit → return immediately) ↓ ④ Cache miss → back to origin ↓ Load balancer → application server ↓ ⑤ App layer: read cache / query database / call downstream APIs ↓ Database / Redis / external services ↓ ⑥ Return the result, all the way back to the browser ↓ Browser: parse HTML → request CSS/JS/images → layout → paint ↑ ⑦ first paint

So the "fast" websites are usually the ones doing these things right:

  • CDN for local delivery: put static assets on the edge node closest to the user — 200ms across an ocean becomes 10ms across a city.
  • HTTP/2, HTTP/3, connection reuse: fewer handshakes, multiplexed streams.
  • Backend caching: hot data lives in Redis, so you don't hit the database every time.
  • Asset optimization: WebP/AVIF for images, code splitting and lazy loading for JS, font subsetting.
  • Critical-path optimization: inline above-the-fold CSS, defer non-critical JS.

And the "slow" websites? Odds are they skipped every one of the above — or stepped on a landmine somewhere (20MB banner video above the fold, one backend call that runs 8 database queries).

Trade-off layer: why is it designed this way?

Performance isn't free. Every "fast" hides a cost:

Adding a CDN

Faster access, but a bigger bandwidth bill every month; cache invalidation has lag; dynamic content doesn't fit.

Adding a cache

QPS goes up, but data may be stale; cache-vs-database consistency bugs are notoriously hard to chase.

Splitting into microservices

Each service scales independently, but one request now crosses several services — network RTT stacks up.

Adding pre-rendering / SSR

First paint is faster, but the server does more work and the architecture gets more complex.

Common mistake: blaming "slow" on "bad servers." In reality, 80% of the slowness comes from frontend assets, DNS/TLS, cross-region and trans-oceanic hops, and the N+1 database queries no one noticed — the server CPU is often sitting idle.

✋ Try it yourself

Give two websites a "health check"

In Chrome, hit F12 → Network panel → check "Disable cache" → then open:

  1. google.com
  2. any small domestic site you find slow

Compare: whose TTFB is longer? Whose assets are bigger? Who makes more requests? Who has no CDN (no x-cache, no cf-ray in Response Headers)?

You'll see with your own eyes — "slow" is never a single cause.

👑 The Grandmaster's View: how does this shape reality?

A slow website = unoptimized complexity, exposed to the user

A fast website isn't fast because it's simple. It's fast because engineers hid the complexity — into the CDN, into the cache, into prefetching, into async loading.

A slow website is slow because engineers had no time, no budget, or simply didn't notice — and dumped the internal complexity straight onto the user.

So performance isn't a pure technical problem. It's a mirror of resources, org structure, and priorities. How far you can push performance depends on how much the company is willing to invest.

Why are big-company websites fast? Not because their engineers are smarter — because they have dedicated SRE teams, dedicated performance budgets, and dedicated UX KPIs watching those few dozen milliseconds.

✨ Back to the question

So, why do some websites open fast and others slow?

Because "opening a website" was never one thing — it's a whole request path.

A fast site is one where every step got real attention;
a slow site is one where some step — or several — got left to no one.

What you feel as "fast or slow" is really the capability profile of a team and its system.
