🌊 Layer 3 · The Engineer's View

Why are big websites always doing monitoring, logging, tracing, and chaos drills?

A system you can't see is a system out of control — chaos drills are vaccines for your system

🤔 The ordinary user's view: why does this matter?

You've probably heard engineers say things like: "No deploys today — we're load testing." "This weekend we're running a full-path chaos drill." "We'll trace this bug by its traceId." To outsiders it sounds like alien code — but this is literally the heartbeat of any big tech company.

In a system with 100 machines and thousands of services, when something breaks, how do you know where it broke? Guess? Pray? The answer — big companies pour insane amounts of effort into one thing: making the system "visible".

The core idea:

A system you can't see is a system out of control.
If you can't "observe" the state of the system, you can't maintain it.
If you've never "rehearsed" a failure, when a real one hits, you're a blind man feeling an elephant.

🎯 Peel it back, layer by layer

The user layer: only the outcome

What ordinary users perceive about observability is: nothing — except that "this service is really stable."

  • 10am one day, Douyin's splash screen flashes white occasionally — you never notice, but the engineers' alerts have already fired 100 times
  • Payments in one region get slow — engineers pull up tracing and see the "payment → risk-control" step's P99 has climbed from 100ms to 2000ms
  • Weibo's servers hit trouble — but the trending hot search "held up," because they'd rehearsed this exact scenario 47 times

The implementation layer: starting to see the structure

The most primitive form of "observing" is — print.

def buy(item_id): print(f"[INFO] user buying item {item_id}") try: result = do_buy(item_id) print(f"[INFO] success: {result}") except Exception as e: print(f"[ERROR] failed: {e}")

That's the crudest form of a log. But when you have 1000 machines, each running tens of thousands of QPS, and billions of log lines scattered everywhere — how do you know "which line is the problem?", "which machines did this one user's request pass through?", "what's the overall state of the system in this exact second?"

So observability evolved along three different "dimensions":

The system layer: seeing the full path

The industry's canonical Three Pillars of Observability:

【Metrics】
→ Time-series numbers — answers "what's the current state?"
→ e.g. QPS, CPU, error rate, P99 latency
→ Tools: Prometheus + Grafana

【Logs】
→ Structured text — answers "what happened?"
→ e.g. detailed info printed by a request, error stack traces
→ Tools: ELK (Elasticsearch + Logstash + Kibana), Loki

【Traces】
→ The full journey of one request — answers "which segment across services is broken?"
→ e.g. an order request: gateway 3ms → user 5ms → inventory 200ms(⚠️) → payment 20ms
→ Tools: Jaeger, SkyWalking, OpenTelemetry

The three are complementary, not substitutes:

Metrics

Shows overall health: Is CPU pegged at 100%? Did the error rate spike?
Strengths: lightweight, long retention, great for alerting.
Weakness: tells you "something's wrong," not "why."

Logs

Shows details: which line of code errored? What's the stack?
Strengths: most complete info, deepest queries.
Weakness: massive volume, expensive to query, hard to stitch across services.

Traces

Shows the path: a request touched 20 services — which segment got slow?
Strengths: visualizes cross-service, cross-machine flow.
Key requirement: a traceId that threads through the full path.

Events / Alerts

Shows changes: When did we deploy? When did we scale out?
Ties "human actions" to "system changes" — the 4th pillar for actual debugging.

A real debugging case: one day P99 latency jumps from 100ms to 800ms.

  1. Check Metrics first — only the payment service's latency has climbed
  2. Then Traces — inside payment, the "call risk-control" step is the slow one
  3. Then Logs — the risk-control service is erroring with "connection pool exhausted"
  4. Cross-reference Events — risk-control shipped a new release half an hour ago
  5. Conclusion: the new release had a bad connection pool config — roll it back

That's a full loop from alert to root cause — without observability, you can't crack it in half an hour, period.

The trade-off layer: why is it built this way?

You might ask: if logs are so great, why not just "record everything"? — because the cost is staggering.

The core trade-off:
Visibility ↔ Cost & performance
The more fine-grained and complete the record, the higher the storage cost and the worse the system performs.
Real systems use sampling — only capture the full detail for, say, 1% of requests.
  • Metrics are "pre-aggregated": no raw data — just the "QPS number per second." Cheap, fast.
  • Logs need sampling and rotation: INFO kept for 7 days, DEBUG for a few hours, expired lines deleted automatically.
  • Traces need head-based sampling: you can't trace every request — usually 1%–10%. But error requests and slow requests are always captured.

💥 Chaos drills: vaccines for your system

After monitoring, logs, and tracing, there's one more "deranged" thing to do: chaos drills (Chaos Engineering) — deliberately injecting failures into your own system.

Thursday, 3pm:

The SRE says: "Drill starts now."
→ Randomly kill 5% of the machines
→ Cut network to one availability zone for 3 minutes
→ Add 500ms to database latency
→ Blow through 10% of the cache

Observe:
· Did alerts fire?
· Did autoscaling kick in?
· Did users see errors?
· How long did recovery take?

This methodology was originally proposed by Netflix. Their famous tool is called Chaos Monkey — it really does randomly break things in production. You might think they're nuts, but their logic is:

"Failures will happen anyway.
Rather than wait for the worst day to find out you weren't ready,
deliberately cause small failures now — see if the system can take them."

That's the idea of "vaccinating the system" — using small, controlled doses of failure to give the system immunity to failure. Alibaba calls it "red-vs-blue"; ByteDance calls it "chaos engineering"; Tencent calls it "failure drills" — different names, same essence.

A common misconception: "the more alerts, the better."
Too many alerts and nobody reads them — this is called "alert fatigue." Good monitoring is: it only fires when a human actually needs to intervene; self-healing problems fix themselves. A single P99 blip shouldn't wake anyone; five minutes of blipping should. One machine at 100% CPU shouldn't page; a cluster averaging 80% should.

✋ Try it yourself

Add a traceId to your own project

In any web app, try this:
1. When a request comes in, generate a UUID and call it traceId.
2. Prepend it to every log line: [trace=abc123] user login.
3. Pass it downstream (via the HTTP header X-Trace-Id).
4. Downstream services also stamp the same traceId into their own logs.

Then, when a user reports "something went wrong with this action," you just ask them for the traceId of that request, and you can search across N services' logs and reconstruct the complete path of that one request — that's the seed of distributed tracing. Once you've felt it, you never go back to the "no-traceId" era of logging.

👑 The Grandmaster's View: how does this shape reality?

A system you can't see is a system out of control

A truth that comes out of Occam's Razor: you can't manage what you can't measure.

This applies to more than systems. It also applies to —

  • Running a company: a CEO without a dashboard is flying blind. KPIs, financials, monthly retrospectives — these are the monitoring for "the company as a system."
  • Personal growth: a person who doesn't "review + record + reflect" spins in place forever. What we call "journaling" is really observability for your life.
  • Governing a country: census, statistics, audits — these are the metrics and logs of "society as a system." Faking the data means the system goes blind.

And "chaos drills" cut even deeper — the philosophy is "admitting you will fail."

A truly powerful system isn't one that "never fails" — it's one that "is constantly making trouble for itself on purpose."

· Fire drills: vaccines for a city
· Military exercises: vaccines for a nation
· Emergency plans: vaccines for an organization
· Retrospectives: vaccines for a team

Every great system that outlasts its era does the same thing: fail deliberately and cheaply, so you don't fail for real and expensively.

✨ Back to the question

So — why are big websites always doing monitoring, logging, tracing, and chaos drills?

Because once a system gets complex enough, "can you see it?" matters more than "did you write it correctly?" Metrics show you "what's happening," Logs show you "the details," Traces show you "the path it took" — and drills mean by the time real failure arrives, you've already rehearsed the response.

The secret of a mature system isn't "never failing" —
it's "when it does fail, you've already run this drill 100 times."

That's also why the most valuable skill of an engineer is never "writing code" —
it's "when the system's on fire, locating the problem in 5 minutes and restoring service in 10."
