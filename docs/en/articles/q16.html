🌊 Layer 3 · The Engineer's View

Why does a seemingly simple like, comment, or checkout button need so many moving parts behind it?

The "simple" the user sees is bought with "complex" on the engineer's side

🤔 An ordinary user's take: why does this matter?

You scroll onto a video, you like it, you tap the heart. The icon turns red, the counter ticks up, you keep scrolling.

Clean, fast — under 100ms. As a user, you'd think: "Isn't this just storing a number +1?"

But in an engineer's eyes, that single like touches at least 10 systems.

Idempotency, deduplication, anti-abuse, counter consistency, recommendation updates, notifications, audit trail… Every "optional-looking" detail is the residue of countless past incidents.

🧩 Peeling it back: break the big problem into small ones

Let's take the smallest feature — "like" — and see how much it's hiding:

  1. Who is tapping? (identity)
  2. What about repeat clicks / network retries? (idempotency)
  3. Is this a bot? (risk control)
  4. How do we write the counter? (consistency vs. performance)
  5. Should the author get a notification?
  6. Should the recommender know? (signal feedback)
  7. Do we need an audit log?
  8. What if a downstream service is down?

🎯 Peel it back, layer by layer

User layer: only the result matters

The user's view is one sentence: "Tap it, and it turns red." That's it.

That "turn red" has to fire in under 100ms — otherwise the user thinks their phone lagged, or thinks the tap didn't register, and taps again. Which creates a whole new problem.

Implementation layer: starting to understand structure

The most naive implementation looks like this:

// Naive version: just +1 function like(userId, postId) { db.execute( 'UPDATE post SET like_count = like_count + 1 WHERE id = ?', [postId] ) }

This code is fine in a tutorial — in production it's an incident waiting to happen. It steps on at least four landmines:

  • No idempotency: a network retry gives you +2, +3.
  • No relation record: no way to tell "has this person already liked it?"
  • Row lock under high concurrency: a hot post with 100k likes/sec has 100k transactions fighting over one row.
  • No decoupling: recommender, notifications — all done synchronously through this one call, so everything blocks.

System layer: seeing the full request path

The real like path looks like this:

[ User taps ] ↓ ① Authentication (JWT / Session) ↓ ② Idempotency check (idempotency key / unique index user_id+post_id) ↓ ③ Risk control / anti-abuse (rate, device fingerprint, behavior signals) ↓ ④ Write the like relation (user_like: userId, postId, ts) ↓ ⑤ Update the counter (Redis INCR fast → async sync back to DB) ↓ ⑥ Publish an event to the message queue (Kafka: post.liked) ↓ ├─→ Notification service (ping the author) ├─→ Recommender service (update the user's interest profile) ├─→ Leaderboard service (heat update) ├─→ Data warehouse (BI analytics) └─→ Audit log (compliance, traceability)

Almost none of these steps are "extra" — each one is the residue of some past incident:

Why idempotency? Because client networks jitter and buttons get mis-tapped.
Why risk control? Because bot farms are out there liking marketing accounts.
Why count in Redis? Because a hot row in MySQL will get jammed by row locks.
Why a message queue? Because there are multiple downstream consumers — you can't wait for all of them synchronously.
Why audit? Because one day there's a lawsuit or a regulator, and you have to say exactly "who liked what, at what time."

Trade-off layer: why design it this way?

What's interesting is that the same "like" can be built completely differently in different products:

WeChat Moments likes

Strong consistency first: your friends have to see "who liked it" — count is small, so just store the relation in the database.

Douyin (TikTok) likes

Eventual consistency first: with hundreds of thousands of likes, nobody cares who tapped — what matters is the counter not stalling. Redis counter + async persistence.

E-commerce checkout

Money transactions: must be strongly consistent, idempotent, rollback-able, reconcilable. DB transaction + distributed lock + state machine.

Livestream hearts (heart rain)

Pure frontend fake motion: don't upload every tap — animate on the client, and the server just samples the count.

Common mistake: "Isn't this just a table with one column? Why so many components?" Because in the real world, a feature isn't defined by requirements — it's defined by scale + edge cases. A "like" for 10 users and a "like" for 100 million users are two completely different systems.

✋ Try it yourself

Do a "complexity dig"

Pick any app you know well (say, some e-commerce app), and run through a checkout. Use a packet-capture tool (Charles / mitmproxy / Chrome DevTools Network) and watch, from "tap checkout" to "payment page appears," how many requests get fired.

You'll probably count 10~30: pre-order, inventory check, coupon match, address validation, risk control, order creation, order-number generation, inventory lock, jump to payment…

Then ask yourself: which of these can you cut? What happens if you do?

👑 The Grandmaster's View: how this shapes reality

The "simple" the user sees is bought with "complex" on the engineer's side

Every truly great product follows one brutal rule: keep the complexity on your side, hand the simplicity to the user.

You think liking is simple — because ByteDance's engineers hid the idempotency, risk control, counter consistency, and async fan-out for you;
You think checkout is smooth — because Taobao's middleware team of hundreds is keeping transactions strongly consistent;
You think WeChat replies instantly — because behind it is a push architecture built up over more than a decade, all the way back to the QQ era.

"Simple" is never free. It means an organization is willing to pour massive engineering complexity into holding up your experience. Next time you look at some feature and think "wow, this is rough" — what you're really rating is how much complexity that company was willing to hide for you.

✨ Back to the question

So — why does a single "like" need so many moving parts?

Because at scale, there are no small features.

Every action that looks simple to the user has to trade off idempotency, consistency, performance, security, audit, and extensibility.
The red heart +1 you see is dozens of systems performing a concerto in the background.
