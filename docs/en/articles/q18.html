Why does the database so often become the system's bottleneck?

The database is the "last one telling the truth" in your system

🤔 The ordinary user's view: why does this matter?

Anyone who's done backend work has heard this line: "80% of performance problems come from the database."

You might think — CPUs aren't expensive, SSDs aren't slow, so why is the database always the one dragging the system down? Can't we just get a better one? Can't we just add more machines?

The database is slow by nature, limited by nature, prone to conflict by nature — and yet it's the only one telling the truth.

All persistence, all transactions, all consistency, all queryability — in the end, everything lands on the database. That's what makes it the most precious and the most fragile link in the whole system.

🧩 Break it down

  1. Where exactly is the database slow? (disk, locks, transactions, connections)
  2. Why can't you scale it by adding machines the way you do with a web service?
  3. What do bottlenecks actually look like in the wild? (slow queries, lock waits, connection pools maxed out)
  4. What tricks do engineers use to route around the bottleneck? (caching, read/write splitting, sharding)

🎯 Peel it back, layer by layer

The user layer: only the symptoms

Users don't say "the database is slow." They say "this app is laggy," "my order is gone," "the payment went through but the page didn't update."

Behind those symptoms, chances are — some SQL took 3 seconds, some table got locked, or some connection pool maxed out.

The implementation layer: how it's built

An ordinary SQL query:

SELECT * FROM orders WHERE user_id = 12345 AND status = 'PAID' ORDER BY created_at DESC LIMIT 20;

What actually happens inside the database?

  1. Parse + optimize: the database decides "which index to use" and "how to sort."
  2. Walk the B+ tree index to find rows where user_id = 12345.
  3. Go back to the table to read the actual row data (unless it's a covering index).
  4. Filter by status, sort, take the top 20.
  5. If another transaction is writing to those rows right now — wait for the lock.

Every step can go wrong. Miss one index, and step 2 becomes a full-table scan over a million rows. If status isn't selective enough, step 4's sort gets slow. Hot-row updates? Step 5's lock waits can stretch into seconds.

The system layer: the full path

The resource ceiling on a single-node database is way lower than you'd think:

The ceiling on a single-node MySQL (rough numbers) ┌──────────────────────────────────────┐ │ Disk IOPS ~10K–100K/s (SSD) │ │ Max connections a few hundred to a few thousand │ │ Row locks one writer per row at a time │ │ Single txn size bounded by undo/redo │ │ Network a few Gbps, tops │ └──────────────────────────────────────┘ Meanwhile the application layer can do: Web tier: add machines, scale horizontally to tens of thousands Cache tier: a single Redis node starts at 100K QPS

Here's the catch: scaling the web tier horizontally is cheap; scaling the database horizontally is expensive. Because the database has to guarantee ACID, and syncing data between machines is a hard problem in itself. So in a real system under real traffic, the database is always the first thing to buckle.

Classic "database bottleneck" scenes:

  • N+1 queries: a list page that queries the detail for every item, one at a time. 10 rows, 11 SQLs. 1000 rows, 1001 SQLs.
  • Slow queries: wrong index, or LIKE '%xxx%', or an ORDER BY with no index behind it — one query, 3 seconds.
  • Lock waits: a flash sale on one item, 10,000 transactions all fighting for the same UPDATE stock row.
  • Connection pool blow-up: one slow query holds a connection forever, and every request behind it just piles up in a queue.
  • Giant transactions: a single transaction stuffed with 10,000 updates — huge lock footprint, painful rollback.

The trade-off layer: why designed this way?

If the database is the bottleneck, what do engineers do about it? The answer is a whole toolbox of ways to route around it:

Add indexes / tune SQL

Cheapest fix, fastest payoff. 80% of slow queries get saved right here.

Add a cache (Redis)

Push reads to memory — the database only handles 20% of read traffic. Cost: consistency gets harder.

Read/write splitting (primary + replicas)

Write to primary, read from replicas. Cost: there's replication lag — the business has to tolerate "reading slightly stale data."

Sharding (ShardingSphere / Vitess)

Cut the data into N pieces across N databases. Cost: cross-shard joins and cross-shard transactions basically don't work anymore.

Switch to NoSQL (MongoDB / HBase)

Give up SQL's strong guarantees in exchange for horizontal scalability. Cost: no transactions, complex queries hurt.

Switch to NewSQL (TiDB / CockroachDB)

Horizontal scale + SQL semantics, both at once. Cost: slightly higher latency, harder ops.

Common mistake: "The database is slow, so let's switch to a beefier database." 90% of the time, the real problem is bad SQL + missing indexes + oversized transactions — no database swap will save you. Run EXPLAIN on your execution plan, use the slow log to catch the top offenders. That's worth way more than switching engines.

✋ Try it yourself

See the cost of a full-table scan with your own eyes

On your local MySQL, build a table with a million rows, insert some data. Then run:

-- No index, full-table scan EXPLAIN SELECT * FROM users WHERE name = 'Alice'; -- Add the index, run it again CREATE INDEX idx_name ON users(name); EXPLAIN SELECT * FROM users WHERE name = 'Alice';

Compare the rows and type columns across the two runs. One is ALL / rows≈1000000, the other is ref / rows≈1. Response time drops from seconds to milliseconds. This is one index saving one business line.

👑 The Grandmaster's View: how does this shape reality?

The database is the "last one telling the truth" in your system

Across the entire application stack, only the database makes this promise: if I said it's saved, it's really saved — even through power loss, crashes, restarts, nothing inside a committed transaction is lost.

Precisely because it carries the "anchor of trust," every complexity in the system eventually piles up on it: consistency, persistence, transactions, locks, recovery, backups, audits. These are the costs of being real.

That's why, inside big companies, you see a strange pattern: business logic can be outsourced, the DBA team never can be. Once the data is wrong, everything else falls with it. The database is the conscience of the system — and the most expensive conscience you'll ever pay for.

Pull the camera back further, and "why is the database a bottleneck?" reveals a universal law — any mechanism that tries to preserve the truth is doomed to be slow, scarce, and fought over. Finance, law, archives, blockchain… underneath, they're all solving the same problem.

✨ Back to the question

So — why does the database so often become the bottleneck?

Because it carries the heaviest responsibility in the system: telling the truth.

And truth-telling is slow, expensive, and hard to scale horizontally by nature.
