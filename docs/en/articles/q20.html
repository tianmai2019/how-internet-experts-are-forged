🌊 Layer 3 · The Engineer's View

Why does caching dramatically boost system performance?

A gamble on time — trading "freshness" for "faster"

🤔 The ordinary user: why does this matter?

Ever notice something weird? The same Taobao product page — first click takes a full second of "loading spinner", second refresh snaps open instantly. The same TikTok video — first swipe buffers for a beat, but come back to it and it never stutters again.

That's not magic. It's something almost every internet system does — caching. It's the secret weapon behind everything that "feels fast."

What is caching, really?

One sentence: stash the result you just computed, so next time you don't have to compute it again.
Time gets "deposited" — the next request "withdraws" it.

Understand caching and you understand why "12306 could survive Spring Festival traffic once they added a cache", why "Weibo's trending list loads instantly", and "what a CDN is even for." It's one of the basic lenses an engineer uses to see the world.

🎯 Peel it back, layer by layer

The user's view: only the outcome

The only thing an ordinary user notices about caching is: "this site feels faster."

A few subtler sensations:

  • First open of a page is a bit slow — after that, it's lightning
  • Offline, some content still shows up (browser cache)
  • Some data on a page "isn't the latest" — a refresh updates it

At this layer, the user can't see the cache. They just feel the "smoothness" it produces.

The implementation view: starting to see structure

The most basic implementation of a cache is a "dictionary you can look things up in fast" — usually a Key-Value structure. The Key is "what you're asking about". The Value is "the answer we computed last time."

# A minimal cache sketch (pseudocode) def get_user(user_id): if cache.has(user_id): # Cache hit: return directly return cache.get(user_id) user = db.query(user_id) # Cache miss: query the database cache.set(user_id, user, ttl=60) # Stash it, reusable for 60 seconds return user

This snippet is basically the entire soul of the "caching pattern." Every other bit of complexity spins around these four lines.

But there's a hidden assumption here: why is "checking the cache" faster than "checking the database"? Because they sit at different tiers on the speed hierarchy:

CPU register ≈ 1 ns
L1 cache ≈ 1 ns
Memory ≈ 100 ns
SSD disk ≈ 100,000 ns (100 microseconds)
Network round trip ≈ 1,000,000 ns (1 millisecond)
Cross-datacenter call ≈ 100,000,000 ns (100 milliseconds)

Top to bottom, each layer is 100x to 1000x slower. Caching is just "move the data from a slow layer to a fast one." That's the physical reason it seems to speed things up out of thin air.

The system view: the full path

In a real internet system, there's never just "one layer of cache" — there's a whole cache chain. Data crosses a full row of caches before it ever touches the database at the bottom.

Browser cache
↓ (already local? return immediately)
CDN (content delivery network — the datacenter is tens of kilometers away from you)
↓
Reverse proxy cache (Nginx / Varnish)
↓
In-process application cache (local memory)
↓
Distributed cache (Redis / Memcached)
↓
Database (MySQL / PostgreSQL)

A request travels top to bottom. Any layer that "hits" turns around and returns immediately — no need to bother the layers below. That's the idea of "multi-layer caching" — the fastest layer catches the most requests.

There's one key metric for judging how good a cache layer is — the hit rate: out of 100 requests coming in, how many got stopped here. Higher hit rate, less pressure downstream. Top-tier CDNs routinely hit 95%+ — meaning the backend only has to handle 5% of the raw traffic.

The trade-off view: why designed this way?

Caching looks like "free" performance — but there's always a cost. A veteran engineer sees a cache and their first thought is — what about data consistency?

The core trade-off of caching:
speed ↔ data freshness
Want faster? You have to tolerate data being "a little stale."
Want absolute accuracy? You give up most of the cache's benefit.

Around this trade-off, there are a few "classic disaster words" you'll run into sooner or later:

Cache penetration

Someone queries a Key that doesn't exist at all. The cache never hits, every request slams the database. A favorite trick of attackers trying to knock a system over.
Fix: cache the "empty result" too.

Cache breakdown

A hot Key suddenly expires, and a flood of requests hit the database at the same instant.
Fix: use a lock to serialize the reload, or extend the TTL for hot data.

Cache avalanche

A huge batch of Keys expires at the same moment, all their requests fall through to the database, which collapses under the load.
Fix: add random jitter to TTLs — avoid "everything expires in the same second."

Dirty reads / consistency

The database gets updated, but the cache still holds the old value — users read the "previous version."
Fix: pick a write policy (Cache-Aside / Write-Through), or use delayed double-delete.

A common mistake: "adding a cache always improves performance."
If your hit rate is below 50%, you're carrying all of a cache's complexity without getting the benefit — and deleting it might actually be faster. Caching isn't "you win by adding it." It's "you only win when it hits."

One layer deeper, there's the locality principle. Caching works because real-world access patterns aren't uniform: a small number of hot items get hit over and over, while a huge tail of cold data goes almost untouched (the "80/20 rule"). That's why caching the hot data is more cost-effective than caching all of it.

✋ Try it yourself

Look at your own browser cache

1. Open Chrome, hit F12 for DevTools, switch to the Network tab.
2. Refresh any site (say, zhihu.com).
3. Look at the "Size" column — plenty of requests will read (disk cache) or (memory cache).
4. Tick Disable cache at the top, then refresh again.
5. Compare the two runs' "total time" and "total size" — the gap can be several times over.

That's it — you just "saw" the real impact of caching on performance.

👑 The Grandmaster's View: how does this shape reality?

Caching = a gamble on time

The philosophy of caching is a lot like "experience" in real life:
our brains remember "last time this worked," and next time we just repeat it instead of reasoning it through again — that's caching.

The cost: when the world changes, you don't know.
Habits make people fast — and also make people dull.

Zoomed up onto the internet, there's an even bigger side effect — caching shapes the world you see. CDNs decide how quickly the news reaches you. Your ISP's DNS cache decides whether a given site is reachable. Even the search results you see have been "frozen" once by some layer of cache.

Cache isn't free speed — it's speed you pay for with freshness. Every engineering effort around it is a careful management of that gamble: the bet is that "the world won't change too fast in the short term."

✨ Back to the question

So — why does caching dramatically boost system performance?

Because it replaces "what we'd have to do next" with "the result we already computed before." Between a CPU register and a cross-datacenter call, every step down the hierarchy is a 100x jump in latency. All caching does is move data a little closer — and the effect is night-and-day faster.

But what actually makes someone an engineer isn't "knowing how to add a cache" —
it's knowing when not to add one —
knowing which data can go stale for a second, and which data can't be wrong for even a moment.
