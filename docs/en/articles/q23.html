🌊 Layer 3 · The Engineer's View

Why are distributed systems so much more complex than single-machine ones?

A single machine is one brain calling the shots. Distributed is a group of brains that has to hold a meeting.

🤔 The ordinary user's angle: why does this matter?

You've probably heard "distributed system" thrown around a lot, but you may not have realized: almost every internet service you use today is, at its core, a distributed system. WeChat, TikTok, Taobao, 12306, Alipay — none of them are "one big computer" serving you.

You may have heard engineers grumble: "This bug only shows up in distributed environments!" "Why don't the numbers match?" — behind those complaints is the kind of hair-losing complexity that distributed systems bring.

The core awkwardness of distributed systems:

Things that are "obvious" on a single machine can all be wrong in distributed land.
For example:
· "Time" isn't globally synchronized
· A "call" doesn't always come back
· "Someone else wrote the data" doesn't mean "you can read it"

🧩 Peel it back: break the big question into small ones

  1. Why is a single machine "simple"? Because there's only one brain deciding.
  2. Does adding one more machine make it complex? Yes — going from 1 to 2 is a qualitative leap.
  3. Why is the network so terrifying? It can be "slow" — and it can "lie" to you.
  4. How does a group of brains agree? That's the consensus problem.

🎯 Peel it back, layer by layer

The user layer: only the outcome matters

A user's experience of a distributed system is usually just a few "strange moments":

  • A Weibo post you just deleted reappears after a refresh (cache inconsistency)
  • A bank transfer says "processing" for a few seconds (waiting for multi-party confirmation)
  • Payment succeeded but the order still shows unpaid (cross-service state delay)
  • A feature works for some people but not others (canary release + partition routing)

These "little bugs" aren't really bugs — they're physical properties of the distributed system itself: state doesn't sync across machines that easily.

The implementation layer: seeing how it's built

The simplest distributed setup is "two machines doing the work together." Looks like just one extra machine? Actually, you've gone from "dictatorship" to "council" — and every coordination problem comes with it.

# Single-machine version: decrement stock, simple and reliable def buy(item_id): lock.acquire() # in-memory lock stock = memory[item_id] if stock > 0: memory[item_id] -= 1 return "success" return "sold_out" lock.release() # Distributed version: two machines selling at once — problems appear def buy(item_id): # The in-memory lock is useless now — each machine has its own memory # You need a "distributed lock" living in shared Redis / Etcd with distributed_lock(item_id): stock = redis.get(item_id) if int(stock) > 0: redis.decr(item_id) return "success" return "sold_out"

Looks like you just added a distributed_lock, but you've opened a whole Pandora's box: What if Redis dies? What if the lock isn't released? What if the two nodes see different stock counts? Every "simple-looking" distributed operation hides a dozen corner cases.

The system layer: seeing the full path

In distributed systems, one theorem gets quoted more than any other — the CAP theorem. It says:

【C】Consistency: every node reads the same, latest data
【A】Availability: every request gets a response (no errors)
【P】Partition tolerance: the system keeps running when the network breaks

CAP theorem: you can only pick two of the three.
Network trouble is inevitable (P is unavoidable),
so the real choice is — sacrifice C or sacrifice A?

These few "invisible enemies" are the root of why distributed systems are insanely complex:

Network Partition

The fiber between two data centers snaps, a router dies, a firewall throws a fit — both sides are still running, but they can't see each other.
The system automatically "splits in half," each half keeps taking customers, and both may modify the same piece of data.

Clock Skew

Every machine has its own clock. NTP sync is only millisecond-accurate, and it drifts.
You can't just "use timestamps to decide who's latest" — Google Spanner literally uses GPS + atomic clocks to dare do global consistency.

Opaque Failures

When a single machine crashes, your process exits — the feedback is clear.
In distributed land, when a call "doesn't return," did the other side never receive it? Still processing? Finished but the reply got lost? You literally can't tell.

State Consistency

Three replicas store different data — what now? Who's right?
You rely on a consensus protocol (Paxos / Raft) — multiple nodes "vote" to decide a value. Writing one line of code takes several network round-trips.

Consensus protocols are the most important and hardest thing in distributed systems: Paxos — proposed by Leslie Lamport in 1989, theoretically perfect but so hard to understand that even Google engineers complain; Raft — the "human-friendly" consensus algorithm from Stanford in 2013, used by Etcd, TiKV, Consul. They solve one core problem — how does a group of independent nodes, over an unreliable network, agree on "what the next value should be"?

The trade-off layer: why was it designed this way?

The most painful thing about distributed complexity isn't that "it's technically hard" — it's that you have to make choices, and every choice hurts.

Real-world distributed choices:

· CP systems (consistency first): ZooKeeper / Etcd. When the network breaks, they'd rather refuse service than serve wrong data. Used for finance, locks, service registries.
· AP systems (availability first): Cassandra / DynamoDB / most e-commerce display layers. Even if data is "eventually consistent," they always respond.
· Somewhere in between: TiDB / Spanner. Raft + optimizations, trying to have their cake and eat it too — at the cost of hardware and network spend.
Common misconception: "Distributed = better, more powerful."
A lot of startups jump straight to microservices + distributed databases, only to find themselves paying "1 billion requests / day" complexity for a "10 thousand requests / day" system. If a single machine works, use one. If primary/replica works, don't build a cluster — distributed is a "reluctant last resort," not a "goal to flex about."

The Fallacies of Distributed Computing (the eight fallacies) are worth memorizing for every engineer:

  1. The network is reliable (❌)
  2. Latency is zero (❌)
  3. Bandwidth is infinite (❌)
  4. The network is secure (❌)
  5. Topology doesn't change (❌)
  6. There is one administrator (❌)
  7. Transport cost is zero (❌)
  8. The network is homogeneous (❌)

Every pain in distributed systems can be traced back to one of these eight lines.

✋ Try it yourself

Feel a "network partition" firsthand

If you have a Linux server nearby, try this:
1. Use iptables to block outbound connections on a port:
sudo iptables -A OUTPUT -p tcp --dport 6379 -j DROP
2. What happens when your app connects to Redis? — it won't error out immediately. It'll just "hang" until TCP times out (30+ seconds by default).
3. Remove the rule: sudo iptables -D OUTPUT -p tcp --dport 6379 -j DROP

This tiny experiment lets you feel it in your bones: "no response" and "responded but slowly" are indistinguishable to the client. That's the source of 99% of the head-scratcher bugs in distributed systems.

👑 The Grandmaster's View: how does this shape reality?

Single machine = one brain. Distributed = a group of brains holding a meeting.

The single-machine world is pure: one brain calls the shots. It gives the orders, it makes the final call, and when something breaks, "where it broke" is crystal clear.

The distributed world is like human society: a group of brains has to hold a meeting. Every brain has its own memory, its own clock, its own biases. To get them to agree, you need meetings, votes, protocols, arbitration. "Complexity" isn't technical redundancy — it's the cost of collaboration.

This insight changes how you see the real world:
· Why does a company hold so many meetings? Because it's a distributed system — consensus has a cost.
· Why is national decision-making slow? Because it's a super-scale distributed system — the consensus cost is astronomical.
· Why is marriage hard? Because it's a 2-node distributed system, and the network often partitions.

Anywhere more than one person makes a decision is a distributed system. And a distributed system's complexity is never a technical problem — it's the political cost of "multi-party coordination."

Engineers who learn CAP, Paxos, and Raft quietly learn something else too:
"All cooperation has a price — if you want it faster, you give up some consistency; if you want zero errors, you accept some waiting."

✨ Back to the question

So, why are distributed systems so much more complex than single-machine ones?

Because "communication" is now part of the job. Unreliable networks, unsynchronized clocks, invisible failures, hard-to-unify state — these aren't programming problems, they're a tax the physical world levies on multi-machine cooperation. A single machine only needs to "get it right." Distributed systems also need to "communicate, reach consensus, and tolerate failure."

Every engineer who goes deep eventually gets it:
Writing distributed code isn't hard. What's hard is "thinking clearly about what state every other node might be in when each action happens."
That's not programming anymore — it's multi-party game theory.
