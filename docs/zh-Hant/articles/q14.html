🌊 第3層認知 · 工程師視角

為什麼有的網站打開很快，有的網站卻總是很慢？

"慢"不是一個原因，而是一整條鏈路的暴露

🤔 小白視角：這個問題為什麼重要？

你一定經歷過：同樣是刷網頁，Google 和百度搜索幾乎瞬間出結果，某些企業官網卻要轉圈 5 秒；淘寶首頁秒開，某個不知名商城點一下要等半天。為什麼？

我們下意識會說："他們服務器不行唄。" 但真的這麼簡單嗎？

"快慢"不是一個數字，而是一條鏈路。

當你按下回車到看到首屏畫面，中間發生了幾十甚至上百件事。 任何一環慢，你看到的都是"這個網站好慢"。

理解"為什麼慢"，就是理解"網站到底是怎麼被組裝出來的"。這是從"用戶視角"邁向"工程師視角"的第一課。

🧩 拆解：把大問題拆成小問題

  1. 找到服務器：DNS 查了多久？
  2. 建立連接：TCP + TLS 花了多久？
  3. 請求路徑：你離服務器多遠？
  4. 後端處理：服務器算出答案花了多久？
  5. 資源體積：HTML、JS、CSS、圖片、字體多大？
  6. 瀏覽器渲染：拿到東西之後，畫出來又花了多久？

🎯 一層一層看

用戶層：只看結果

普通用戶只有一個感受："快"或"慢"。他不會區分"是 DNS 慢還是渲染慢"，他只知道白屏時間超過 3 秒，他就走了。

Google 早在 2009 年就發現：頁面加載多 400ms，用戶流失 0.6%。亞馬遜估算過：延遲每多 100ms，銷售額損失 1%。

實現層：開始理解構造

打開 Chrome 開發者工具的 Network 面板，選一個請求，你會看到一根 Waterfall 瀑布圖：

Request: https://example.com/index.html ├── Queueing 2 ms ├── DNS Lookup 35 ms ← 找服務器 ├── Initial connection 80 ms ← TCP 三次握手 ├── SSL 120 ms ← TLS 握手 (HTTPS) ├── Request sent 1 ms ├── Waiting (TTFB) 240 ms ← 服務器在算 └── Content Download 45 ms ← 下載 HTML 總計: ~523 ms

這就是一次請求的"體檢報告"。TTFB（Time To First Byte）反映後端速度，Content Download反映資源體積和網速，DNS / SSL反映連接建立開銷。

系統層：看到完整鏈路

真實的一次"打開網站"，是一場接力賽。任何一棒掉鏈子都會拖垮全程：

用戶瀏覽器 ↓ ① DNS 解析（可能 5ms，也可能 300ms） ↓ ② TCP + TLS 握手（跨洋網絡 → 200ms+） ↓ ③ 請求發出，經過運營商、骨幹網、CDN 邊緣節點 ↓ CDN 邊緣節點（可能命中緩存，直接返回） ↓ ④ 未命中 → 回源 ↓ 負載均衡器 → 應用服務器 ↓ ⑤ 應用層：讀緩存 / 查數據庫 / 調下游 API ↓ 數據庫 / Redis / 外部服務 ↓ ⑥ 返回結果，一路走回瀏覽器 ↓ 瀏覽器：解析 HTML → 請求 CSS/JS/圖片 → 佈局 → 繪製 ↑ ⑦ 首屏繪製

所以"快"的網站通常做對了這些事：

  • CDN 就近分發：把靜態資源放到離用戶最近的邊緣節點，從跨洋 200ms 變成同城 10ms。
  • HTTP/2、HTTP/3、連接複用：減少握手次數，多路複用。
  • 後端緩存：熱點數據放 Redis，避免每次都查數據庫。
  • 資源優化：圖片走 WebP/AVIF、JS 拆包懶加載、字體子集化。
  • 關鍵路徑優化：首屏 CSS 內聯，非關鍵 JS 延後執行。

而"慢"的網站，大概率是把上面每一項都省了——或者恰好在某一環節裡踩了雷（比如首屏加載 20MB 的 banner 視頻、後端一次調用查了 8 次數據庫）。

權衡層：為什麼這樣設計？

性能不是免費的。每一個"快"的背後都藏著代價：

用了 CDN

訪問快了，但每月要多付一筆帶寬費；緩存刷新有滯後；動態內容不適合。

加了緩存

QPS 上去了，但數據可能不新鮮；緩存與數據庫不一致的 bug 極其難查。

拆分了微服務

每個服務獨立擴容，但一次請求要跨多個服務，網絡 RTT 累加。

用了預渲染 / SSR

首屏快了，但服務端壓力更大，架構更復雜。

常見誤區：把"慢"直接歸罪於"服務器不好"。實際情況裡，80% 的慢來自前端資源、DNS/TLS、跨域跨洋、以及被忽視的 N+1 數據庫查詢——服務器 CPU 反而經常閒著。

✋ 動手試試

給兩個網站做一次"體檢"

在 Chrome 裡按 F12 → Network 面板 → 勾選 "Disable cache" → 分別打開：

  1. google.com
  2. 任一你覺得慢的國內小網站

對比看：誰的 TTFB 更長？誰的資源體積更大？誰請求數更多？誰沒用 CDN（Response Headers 裡沒有 x-cache、cf-ray 之類）？

你會親眼看到——"慢"從來不是一個原因。

👑 大帝視角：這如何塑造現實？

慢網站 = 未被優化的複雜度，暴露給了用戶

一個網站快，不是因為它簡單，而是因為工程師把複雜度藏起來了——藏進了 CDN、藏進了緩存、藏進了預取、藏進了異步加載。

一個網站慢，是因為工程師沒時間、沒預算、或者乾脆沒意識到，把內部複雜度直接甩給了用戶去承擔。

所以性能不是純技術問題，它是資源、組織、優先級的映射。你能看到多遠的性能優化，取決於公司願意投入多少。

大廠網站為什麼快？不是因為工程師更聰明，是因為他們有專門的 SRE 團隊、專門的性能預算、專門的用戶體驗 KPI 在盯著這幾十毫秒。

✨ 回到問題

所以，為什麼有的網站快，有的網站慢？

因為"打開網站"從來不是一件事，而是一整條鏈路。

快的網站，是每一環都被認真優化過；
慢的網站，是某一環——或者好幾環——沒人管。

你看到的"快慢"，其實是團隊與系統的能力剖面。
