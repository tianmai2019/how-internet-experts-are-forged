為什麼數據庫常常會成為系統的瓶頸？

數據庫是系統裡"最後一個說真話的人"

🤔 小白視角：這個問題為什麼重要？

做過後端的人，幾乎都聽過這句話："性能問題，80% 出在數據庫。"

你可能會想：CPU 又不貴，SSD 又不慢，為什麼數據庫老是拖後腿？換個更好的行不行？加機器行不行？

數據庫天生就是慢的、有限的、易衝突的——但它又是唯一說真話的人。

所有的持久化、事務、一致性、可查詢，最終都要落到它那裡。這就註定它是系統裡最珍貴、也最脆弱的一環。

🧩 拆解：把大問題拆成小問題

  1. 數據庫慢在哪裡？（磁盤、鎖、事務、連接）
  2. 為什麼加機器不能像 Web 服務那樣簡單？
  3. 常見的瓶頸現場有哪些？（慢查詢、鎖等待、連接打滿）
  4. 為了繞開瓶頸，工程師用了哪些手段？（緩存、讀寫分離、分庫分表）

🎯 一層一層看

用戶層：只看結果

用戶不會說"數據庫慢"，他們會說"這個 App 卡"、"我的訂單不見了"、"付款成功了但頁面還沒跳"。

這些症狀背後，大概率就是某條 SQL 執行了 3 秒、某張表被鎖住了、某個連接池打滿了。

實現層：開始理解構造

一句普通的 SQL：

SELECT * FROM orders WHERE user_id = 12345 AND status = 'PAID' ORDER BY created_at DESC LIMIT 20;

它在數據庫裡發生了什麼？

  1. 解析 + 優化：數據庫要決定"用哪個索引"、"怎麼排序"。
  2. 去 B+ 樹索引裡找 user_id = 12345 的行。
  3. 回表讀實際數據行（如果不是覆蓋索引）。
  4. 過濾 status、排序、取前 20 條。
  5. 如果這時有其他事務在寫這些行——要等鎖。

每一步都可能變慢。少一個索引，第 2 步就變成全表掃描 100 萬行；status 不選擇性高，第 4 步排序會慢；有熱點行更新，第 5 步鎖等待可能達到秒級。

系統層：看到完整鏈路

單機數據庫的資源天花板，比想像中低得多：

單機 MySQL 的天花板（粗略估算） ┌──────────────────────────────────────┐ │ 磁盤 IOPS ~10K–100K/s（SSD） │ │ 連接數上限 幾百到幾千 │ │ 行鎖 一行同時只能一個寫者 │ │ 單事務大小 受 undo/redo 影響 │ │ 網絡帶寬 幾 Gbps 頂天 │ └──────────────────────────────────────┘ 而應用層可以做到： Web 層：加機器就能橫向擴展到幾萬臺 緩存層：Redis 單機 10 萬 QPS 起

問題來了：Web 層橫向擴展很便宜，數據庫橫向擴展很貴。因為數據庫要保證 ACID，機器之間同步數據本身就是一件難事。所以真實系統裡流量湧進來，最先撐不住的永遠是數據庫。

典型的"數據庫瓶頸現場"：

  • N+1 查詢：一個列表頁，每一項再單獨查一次詳情。10 條數據、11 次 SQL；1000 條數據、1001 次 SQL。
  • 慢查詢：加錯了索引、或者 LIKE '%xxx%'、或者 ORDER BY 沒索引撐，一條查詢 3 秒。
  • 鎖等待：秒殺一件商品，1 萬個事務搶同一行 UPDATE stock。
  • 連接池爆炸：某個慢查詢把連接佔著不放，後面的請求全排隊。
  • 大事務：一個事務裡塞了 1 萬條 update，鎖範圍極大，回滾極痛。

權衡層：為什麼這樣設計？

既然數據庫是瓶頸，工程師怎麼辦？答案是一整套繞開策略：

加索引 / SQL 優化

成本最低，收益最快。80% 的慢查詢靠這個就能救。

加緩存（Redis）

把讀打到內存，數據庫只承擔 20% 的讀流量。代價：一致性更難。

讀寫分離（主從）

寫主庫、讀從庫。代價：主從有延遲，業務要能接受"讀到舊數據"。

分庫分表（ShardingSphere / Vitess）

數據切成 N 份分佈到 N 個庫。代價：跨庫 join、跨庫事務幾乎不能用了。

換 NoSQL（MongoDB / HBase）

放棄 SQL 的強約束，換水平擴展性。代價：不再有事務、複雜查詢很痛。

換 NewSQL（TiDB / CockroachDB）

兼顧橫向擴展 + SQL 語義。代價：延遲略高，運維複雜。

常見誤區："數據庫慢，就換更牛的數據庫。" 90% 的情況下，問題在SQL 寫得爛 + 索引沒建對 + 事務範圍太大——換任何數據庫都救不了你。用 EXPLAIN 看執行計劃、用慢日誌抓 top 慢 SQL，效果遠大於換引擎。

✋ 動手試試

親眼看到一次全表掃描的代價

在本機 MySQL 建一個 100 萬行的表，插入一些數據。然後跑：

-- 無索引，全表掃描 EXPLAIN SELECT * FROM users WHERE name = 'Alice'; -- 加索引再看一次 CREATE INDEX idx_name ON users(name); EXPLAIN SELECT * FROM users WHERE name = 'Alice';

對比兩次的 rows 和 type：一次是 ALL / rows≈1000000，一次是 ref / rows≈1。響應時間從秒級掉到毫秒級。這就是一個索引救一條業務命。

👑 大帝視角：這如何塑造現實？

數據庫，是系統裡"最後一個說真話的人"

整個應用架構裡，只有數據庫承諾：只要我說存了，就是真的存了——即使斷電、宕機、重啟，事務邊界之內的東西不會丟。

正因為它承擔了這個"信任錨"的角色，所有的複雜都最終壓到它頭上：一致性、持久化、事務、鎖、恢復、備份、審計。這些都是"真實"的代價。

所以在大廠裡，你會看到一個奇特的現象：業務邏輯可以外包，DBA 團隊永遠不會。因為一旦數據錯了，什麼都完了。數據庫是系統的良心，也是系統裡最貴的良心。

從更遠的視角看，"為什麼數據庫是瓶頸"這個問題，其實揭示了一個通用規律——任何試圖保存真相的機制，都註定是慢的、稀缺的、被爭搶的。金融、法律、檔案、區塊鏈……本質上都在解決同一個問題。

✨ 回到問題

所以，為什麼數據庫常常成為瓶頸？

因為它承擔著系統裡最重的責任：說真話。

而說真話是慢的、昂貴的、天生難以橫向擴展的。
工程師的一半時間，都花在"如何在保住數據庫真話的前提下，讓應用不慢"上——這就是 Q17 裡那六件套存在的根本原因。
