為什麼高併發場景下，最難的不是功能實現，而是穩定性保障？

功能是顯性成本，穩定性是隱性資產

🤔 小白視角：這個問題為什麼重要？

你有沒有見過這種"神操作"——某個新出的抽獎小程序，功能看起來一樣簡單：點一下按鈕，抽個獎。但一到抽獎的整點，頁面直接白屏、崩潰、502、"服務器繁忙"……

同樣是"點一下按鈕"，為什麼阿里的雙 11、騰訊的紅包、12306 的搶票能扛住？ 不是因為它們"功能更強"，而是因為它們的"穩定性投入"是新手小程序的成千上萬倍。

核心真相：

做出功能，可能只要 1 天。
做出"1 億人同時用還不崩"的功能，可能要 1 年。
功能是加法，穩定性是乘法——每加一個 9，成本翻倍。

🧩 拆解：把大問題拆成小問題

  1. "可用性"到底怎麼衡量？ "4 個 9"是什麼意思？
  2. 為什麼併發一上去，一切都變了？ 單個請求正常，多個請求為啥就崩？
  3. 穩定性靠什麼？ 是靠"更好的代碼"嗎？
  4. 為什麼大公司都在做"故障演練"？ 主動搞事情？

🎯 一層一層看

用戶層：只看結果

用戶對穩定性的期待，是一條非常殘酷的曲線——

  • 系統正常 100 次，他不會誇你
  • 系統崩了 1 次，他會罵你並且轉告 10 個人
  • 崩在關鍵時刻（付款、搶票、領獎），他會永遠記住

這就是為什麼"看不見的穩定性"，永遠比"看得見的功能"更重要。 功能是加分項，穩定性是不出現就沒人誇、一齣現就是災難的底線。

實現層：開始理解構造

工程師最初會以為——"我把代碼寫好，測試都過了，不就穩定了嗎？" 然後被現實教育：

# 單個請求：完美運行 def buy(item_id, user_id): stock = db.query("SELECT stock FROM items WHERE id=?", item_id) if stock > 0: db.execute("UPDATE items SET stock=stock-1 WHERE id=?", item_id) return "success" # 一萬個請求同時來：超賣了！ # - 都讀到 stock = 5 # - 都執行 stock - 1 # - 結果賣出了 10000 件，實際只有 5 件

這就是併發把簡單問題變複雜的經典例子。 同樣的代碼，1 個人用是對的，10000 個人同時用就是錯的。 穩定性問題的第一課是——"正確"是有條件的。

系統層：看到完整鏈路

衡量穩定性有一個業界通用的語言——可用性 SLA。它用"幾個 9"表示一年可以宕機多久：

99%（2 個 9）→ 每年宕機 87.6 小時（≈ 3.65 天）
99.9%（3 個 9）→ 每年宕機 8.76 小時
99.99%（4 個 9）→ 每年宕機 52.6 分鐘 ⬅ 電商標配
99.999%（5 個 9）→ 每年宕機 5.26 分鐘 ⬅ 金融/電信
99.9999%（6 個 9）→ 每年宕機 31.5 秒 ⬅ 天價

多一個 9，成本可能指數級上升。因為你不再和"代碼錯誤"鬥爭，而是要和光速、磁盤、宇宙射線、人為失誤等所有小概率事件鬥爭。

另外兩個關鍵指標：

  • MTBF（Mean Time Between Failures）：平均無故障時間——衡量"多久出一次事"。
  • MTTR（Mean Time To Recovery）：平均恢復時間——衡量"出事之後多久能好"。

有意思的是，現代互聯網公司大多不再幻想"MTBF 無限大"（永遠不出事），而是拼命降低 MTTR（出事了 30 秒內恢復）。這是一種成熟的哲學轉向：從"避免失敗"到"快速恢復"。

穩定性保障的完整"武器庫"大致是這樣：

限流 + 熔斷 + 降級

限流：每秒最多 1000 個請求進來。
熔斷：下游 5 秒都在超時，直接不再調用。
降級：非核心功能先關掉，保住主鏈路。
三件套是高併發系統的"命門"。

故障域隔離

把系統切成多個"故障單元"（多機房、多可用區），一個掛了其他還能跑。
不要把所有雞蛋放一個籃子。

容量規劃

預估峰值 QPS、精確到 CPU/內存/帶寬，然後預留 3~5 倍容量。
雙 11 之前幾個月，阿里就在做"容量壓測"。

發佈策略

不要全量發佈。用灰度（先 1%，再 10%，再 100%）、金絲雀（一小撮用戶先試）、藍綠部署（兩套環境切流）來降低出事概率。

權衡層：為什麼這樣設計？

穩定性保障最反直覺的一點是——你要主動"變慢"、主動"拒絕服務"、主動"少做點事"。

核心權衡：
讓每個請求都成功 ↔ 讓整個系統不崩
兩者不可兼得。
真正穩定的系統，會主動拒絕一部分請求，來保護自己不進入雪崩狀態。

典型的例子——微博熱搜爆了怎麼辦？不是"讓所有人都能刷"，而是：

  • 先限流，多餘的請求直接返回"稍後再試"
  • 降級：熱搜列表暫時不實時更新，用緩存裡的靜態版本
  • 熔斷：如果推薦系統超時，就跳過它，只返回基礎內容
  • 擴容：緊急拉起備用機器，擴大處理能力

這些操作的哲學都是一樣的：寧可讓 10% 的人稍等，也別讓 100% 的人全掛。

常見誤區："我把代碼寫好、測試寫全，就是穩定了"。
穩定性不是代碼質量問題，是系統性問題。它涉及： 網絡、硬件、依賴、部署、發佈、監控、恢復……一個環節沒考慮，全盤皆輸。 你可能永遠查不出"為什麼週三下午 3 點系統會抖一下"——直到有人告訴你那時候正好在批量重啟一個下游服務。

✋ 動手試試

用 wrk 壓一壓你自己的服務

如果你有一個 Web 服務（哪怕是 Flask hello world），試試：
1. 安裝 wrk：brew install wrk（Mac）
2. 運行壓測：wrk -t4 -c1000 -d30s http://localhost:8080/
（4 個線程，1000 個併發連接，壓 30 秒）
3. 觀察結果：QPS、平均延遲、P99 延遲、錯誤率
4. 逐步加壓：-c 2000、-c 5000……直到你看到錯誤率飆升。

這一步做完，你就知道自己寫的"簡單接口"，其實在什麼併發量下會崩。 這是穩定性思維的第一次覺醒——不要問"能不能跑"，要問"能扛多少"。

👑 大帝視角：這如何塑造現實？

功能是顯性成本，穩定性是隱性資產

新工程師對功能有一種迷之驕傲—— "我一個下午就實現了別人一週做的東西！" 然後他會發現，這個東西在真實流量下 1 分鐘就掛了。

資深工程師看待"功能"時，會不自覺多算一筆賬：
· 這個功能上線後，多幾倍的下游調用？
· 高峰期能扛多少？
· 出錯時如何恢復？
· 會不會引起雪崩？

"功能"是老闆能看見的、能吹的，是顯性成本。
"穩定性"是沒人誇、但是命根子的，是隱性資產。

這個視角推廣到現實社會同樣成立：
· 一家餐廳——菜好吃很重要（功能），但"從不食物中毒"更重要（穩定）。
· 一段婚姻——浪漫時刻是加分項，但"吵架不冷戰"是底線（穩定）。
· 一個國家——GDP 增長是顯性成就，但"社會不動盪"才是根本（穩定）。

所有真正偉大的系統，都不是"能做多驚豔"，而是"能在最糟的時刻依然靠譜"。 你在互聯網大廠看到的所有"看似過度設計"的東西——多機房、多副本、演練、灰度、熔斷—— 都不是給你炫技的，是給"最壞那天"準備的保險單。

✨ 回到問題

所以，為什麼高併發場景下，最難的不是功能實現，而是穩定性保障？

因為功能是有限維的問題，穩定性是無窮維的問題。 你要防的不再是"這行代碼錯沒錯"，而是"流量突增、依賴掛掉、機器炸了、網絡抖動、發佈出錯、誤操作"等等等等無數種小概率事件的組合。 每多防一種，成本翻一番；每漏一種，可能全盤皆輸。

成長的分水嶺在這裡：
初級工程師問："這個功能能實現嗎？"
資深工程師問："這個功能在最糟的一天能實現嗎？"

前者做的是"功能"，後者做的是"系統"。
