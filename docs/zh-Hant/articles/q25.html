為什麼大型網站總是在做監控、日誌、鏈路追蹤和故障演練？

看不見的系統 = 失控的系統；故障演練是給系統打疫苗

🤔 小白視角：這個問題為什麼重要？

你可能聽過程序員這樣說："今天不上線，我們要壓測。""週末做一次全鏈路故障演練。""這個 bug 我們看鏈路 traceId 排查。" 外行聽起來像天書，但這些其實是大廠運轉的"心跳"。

在 100 臺機器、幾千個服務的系統裡，出了問題，你怎麼知道是哪出問題？靠猜？靠命？ 答案是——大公司花了海量精力，就為了做一件事：讓系統"看得見"。

核心觀點：

看不見的系統，等於失控的系統。
你如果不能"觀察到"系統的狀態，你就沒法維護它。
你如果沒有"預演過"故障，它真來了你就是瞎子摸象。

🧩 拆解：把大問題拆成小問題

  1. 系統裡到底有什麼東西"看不見"？
  2. 監控、日誌、追蹤——到底有什麼區別？
  3. 一次故障到底怎麼排查？
  4. 為什麼要"故意搞壞"自己的系統？

🎯 一層一層看

用戶層：只看結果

用戶對可觀測性的感知是：什麼都感覺不到，但結果就是"這家的服務真穩"。

  • 某天 10 點開始，抖音開屏偶爾白屏——你不會看到，但工程師的告警已經響了 100 次
  • 某個地方支付有延遲——工程師從鏈路追蹤看到"支付 → 風控"那一步 P99 從 100ms 漲到了 2000ms
  • 某次微博服務器出問題——熱搜可能"扛住"了，因為演練過 47 次類似場景

實現層：開始理解構造

最原始的"觀察"就是——print。

def buy(item_id): print(f"[INFO] user buying item {item_id}") try: result = do_buy(item_id) print(f"[INFO] success: {result}") except Exception as e: print(f"[ERROR] failed: {e}")

這就是日誌（Log）最樸素的樣子。 但當你有 1000 臺機器、每臺 QPS 上萬時，幾十億行日誌散落各處—— 你怎麼知道"哪一行是問題？"、"哪一個用戶的請求走過哪些機器？"、"這一秒系統整體是什麼狀態？"

於是，可觀測性演化出了三個不同"維度"：

系統層：看到完整鏈路

業界公認的可觀測性三支柱（Three Pillars of Observability）：

【Metrics 指標】
→ 時序數字，回答"現狀"
→ 例：QPS、CPU、錯誤率、P99 延遲
→ 工具：Prometheus + Grafana

【Logs 日誌】
→ 結構化文本，回答"發生了什麼"
→ 例：某個請求打印的詳細信息、報錯堆棧
→ 工具：ELK（Elasticsearch + Logstash + Kibana）、Loki

【Traces 鏈路追蹤】
→ 一次請求的全流程，回答"跨服務的問題在哪一段"
→ 例：一個下單請求：網關 3ms → 用戶 5ms → 庫存 200ms(⚠️) → 支付 20ms
→ 工具：Jaeger、SkyWalking、OpenTelemetry

三者是互補的，不是替代關係：

Metrics（指標）

看整體健康度：CPU 是不是 100%？錯誤率有沒有漲？
特點：輕量、能長期存、適合告警。
缺點：只能告訴你"有問題"，不告訴你"為什麼"。

Logs（日誌）

看細節：哪一行代碼報錯？堆棧是什麼？
特點：信息最全、能查最深。
缺點：量太大、查詢貴、跨服務時難串起來。

Traces（追蹤）

看路徑：一次請求經過了 20 個服務，哪一段慢了？
特點：跨服務、跨機器可視化。
關鍵：需要traceId 貫穿全鏈路。

Events / Alerts

看變化：什麼時候發佈過？什麼時候擴容過？
把"人為動作"和"系統變化"關聯起來，是排查故障的第 4 支柱。

真實排查案例：某天 P99 延遲從 100ms 漲到 800ms。

  1. 先看 Metrics——發現只有支付服務的延遲漲了
  2. 再看 Traces——發現是支付服務裡"調用風控"那一步慢
  3. 再看 Logs——找到風控服務的報錯："connection pool exhausted"
  4. 關聯 Events——發現半小時前風控服務發佈了新版本
  5. 結論：新版本連接池配置錯了，回滾

這就是一次"從告警到根因"的完整閉環——沒有可觀測性，這半小時你根本查不出來。

權衡層：為什麼這樣設計？

你可能會問：既然日誌這麼好，為啥不"啥都記下來"？——因為代價驚人。

核心權衡：
觀察力 ↔ 成本 & 性能
記得越細越全，存儲成本越高、系統性能越差。
真實系統會做採樣——只記錄 1% 的請求詳情。
  • Metrics 是"預聚合"：不存原始數據，只存"每秒的 QPS 數值"。便宜、快。
  • Logs 需要採樣和輪轉：INFO 保留 7 天，DEBUG 只保留幾小時，超時自動刪除。
  • Traces 需要頭部採樣：不能每個請求都追蹤，通常只追 1%~10%，但"錯誤請求"和"慢請求"永遠採。

💥 故障演練：給系統打疫苗

做完了監控、日誌、追蹤，還有一件"變態"的事：故障演練（Chaos Engineering）——主動往自己的系統裡注入故障。

週四下午 3 點：

運維工程師："今天演練開始。"
→ 隨機殺掉 5% 的機器
→ 讓某個可用區斷網 3 分鐘
→ 讓數據庫延遲漲 500ms
→ 讓緩存擊穿 10%

觀察：
· 告警響了嗎？
· 有沒有自動擴容？
· 用戶端有沒有報錯？
· 恢復用了多久？

這個方法論最早由 Netflix 提出，他們的著名工具叫 Chaos Monkey——真的會在生產環境隨機搞破壞。 你可能覺得瘋了，但他們的邏輯是：

"故障總會發生的。
與其等到最壞那天才發現自己沒準備好，
不如現在主動製造小故障，看看系統能不能扛住。"

這就是"給系統打疫苗"的思想——用小劑量、可控的故障，讓系統產生對故障的免疫力。 阿里叫"紅藍對抗"、字節叫"混沌工程"、騰訊叫"故障演習"——名字不同，本質相同。

常見誤區："監控告警越多越好"。
告警一多，就沒人看了——這叫"告警疲勞"。真正好的監控是：只在需要人工介入時才響，能自愈的問題讓系統自己修。 比如 P99 抖一下不用響，抖 5 分鐘才響；單機 CPU 100% 不用響，整個集群平均 80% 才響。

✋ 動手試試

給你自己的項目加一個 traceId

在任意一個 Web 應用裡試試：
1. 請求進來時生成一個 UUID，叫 traceId。
2. 把它塞到日誌的每一行前面：[trace=abc123] user login。
3. 傳給下游服務（用 HTTP Header X-Trace-Id）。
4. 下游也把這個 traceId 打到自己的日誌裡。

然後，當某個用戶報"這次操作有問題"時，你只需要問他要那次請求的 traceId， 就能在 N 個服務的日誌裡搜出他這一次請求的完整路徑—— 這就是鏈路追蹤的雛形。 一旦體會過，你就再也回不去"沒有 traceId"的日誌時代了。

👑 大帝視角：這如何塑造現實？

看不見的系統 = 失控的系統

一個大道至簡的真理：你無法管理你無法測量的東西。

這句話不只適用於系統，也適用於——

  • 公司管理：沒有儀表盤的 CEO，就是在盲開飛機。KPI、財報、月度復盤——都是"公司這個系統"的監控。
  • 個人成長：沒有"復盤 + 記錄 + 反思"的人，永遠原地打轉。所謂"日誌"，其實就是你人生的可觀測性。
  • 國家治理：普查、統計、審計——都是"社會這個系統"的 metrics 和 logs。數據造假，等於系統瞎眼。

而"故障演練"更是深刻——它的哲學是"承認自己會出錯"。

一個真正強大的系統，不是"從不出問題"的系統，而是"總在故意找自己麻煩"的系統。

· 消防演習：給城市打疫苗
· 軍事演習：給國家打疫苗
· 應急預案：給組織打疫苗
· 復盤會：給團隊打疫苗

凡是偉大的、能穿越週期的系統，都在做一件事：主動地、廉價地失敗，來避免真實的、昂貴的失敗。

✨ 回到問題

所以，為什麼大型網站總是在做監控、日誌、鏈路追蹤和故障演練？

因為系統一旦複雜到某個程度，"能不能看見"比"寫沒寫對"更重要。 Metrics 讓你看到"發生了什麼"、Logs 讓你看到"細節是什麼"、Traces 讓你看到"路徑怎麼走的"，而演練讓你在"真實故障來臨前"就已經準備好了應對方案。

成熟系統的秘密不是"從不出錯"，
而是"出錯時你早就演練過 100 遍"。

這也是為什麼工程師最貴的能力，從來不是"寫代碼"，
而是"在系統著火時，5 分鐘內定位問題、10 分鐘內恢復服務"。
