註冊、登錄、評論、點贊、下單……本質上是怎麼實現的?

互聯網世界裡,幾乎所有功能都是"老磚塊的新排列"

🤔 小白視角:這個問題為什麼重要?

你在淘寶下單、在微博點贊、在小紅書評論、在知乎登錄……表面上看,這些是五種完全不同的功能。 但如果告訴你——它們背後其實是同一套東西——你會不會有點驚訝?

這個問題重要,是因為一旦你識別出這套"底層磚塊",你會發現: 所謂"新產品的功能",大多都是老磚塊的重新排列。 這種"看穿"的能力,是從"用產品的人"變成"造產品的人"的分水嶺。

核心洞察:

所有這些功能,歸納起來只有四種操作:
Create(創建)、Read(讀取)、Update(更新)、Delete(刪除)
簡稱 CRUD——加上"知道你是誰"(認證)和"知道你能幹什麼"(授權),幾乎能拼出整個互聯網。

🧩 拆解:把大問題拆成小問題

  1. 不同功能之間,共同的抽象是什麼?
  2. "你是誰"這件事,系統怎麼記住?
  3. "點贊"和"評論"看起來不一樣,底層為啥說是一回事?
  4. 下單為什麼比點贊"重"很多?"重"在哪兒?

🎯 一層一層看

用戶層:只看結果

你覺得:

  • 註冊——填個手機號,創建了賬號
  • 登錄——輸入密碼,進入了世界
  • 評論——寫點字,發出去
  • 點贊——按一下,變紅
  • 下單——選商品、付款、等發貨

看起來是五件不同的事。但工程師眼裡……

實現層:開始理解構造

我們把這五個功能"翻譯"成 CRUD 操作,你會看到魔法:

📝 註冊

Create 一條 users 記錄

INSERT INTO users(phone, password_hash) VALUES(?, ?)

🔑 登錄

Read users 表 + 發一個 token

SELECT id FROM users WHERE phone=? AND password_hash=?

💬 評論

Create 一條 comments 記錄

INSERT INTO comments(user_id, post_id, text) VALUES(?, ?, ?)

❤️ 點贊

Create 一條 likes 記錄(取消贊就 Delete)

INSERT INTO likes(user_id, post_id) VALUES(?, ?)

🛒 下單

Create orders + Update inventory + Create payment……

比較複雜,但每一步都是 CRUD。

💡 結論

互聯網的絕大多數功能 = CRUD 的組合 + 認證 + 一些業務規則

驚不驚喜?讓我們看得更深一點——先看"登錄"到底是怎麼"記住你"的。

"你是誰"這件事:session vs token

HTTP 是一個無狀態協議——服務器每次收到你的請求,都像失憶了一樣,不知道你是誰。 所以,系統必須想辦法在每次請求時"證明你是誰"。目前有兩種主流做法:

🎟️ Session(會話)

登錄後,服務器生成一個 session id,存在它自己的數據庫裡。

下發給你一個 cookie。每次請求,瀏覽器帶上 cookie,服務器去查。

就像"寄存牌"——牌子在你手裡,東西在店裡。

🪪 Token(令牌,JWT)

登錄後,服務器簽發一個加密串(裡面藏著"你是 user_123, 有效到 xxx"),交給你。

每次請求帶上,服務器驗籤就行,不需要查庫。

就像"身份證"——真偽一看就知道。

前端代碼裡,登錄後通常長這樣:

// 登錄成功後,把 token 存起來 const res = await fetch('/api/login', { method: 'POST', body: JSON.stringify({ phone, password }) }); const { token } = await res.json(); localStorage.setItem('token', token); // 之後所有請求都自動帶上 await fetch('/api/comments', { headers: { 'Authorization': `Bearer ${token}` }, method: 'POST', body: JSON.stringify({ postId: 42, text: '好文!' }) });

系統層:看到完整鏈路

我們放大一次"下單"——因為它最能體現工程師如何把 CRUD 組合成"複雜功能":

① 認證 · 你是誰?
↓
② 校驗 · 商品還在嗎?
↓
③ 扣庫存 · Update inventory
↓
④ 創建訂單 · Create orders
↓
⑤ 發起支付 · 調用第三方
↓
⑥ 更新訂單狀態 · Update
↓
⑦ 通知商家發貨

重點來了:下單和點讚的本質區別是——

冪等性 · 事務性 · 一致性

點贊:同一個人點兩次和一次沒差別(去重就行) → 冪等
下單:你重複點"支付",絕不能收兩次錢 → 必須嚴格冪等
下單:扣庫存和創建訂單必須同時成功或同時失敗 → 事務
下單:數據庫、庫存、支付、商家四個系統,數據要"最終對得上" → 一致性

所以一個"下單"接口,可能有幾十甚至幾百行代碼,內部小心翼翼地處理各種失敗場景。 但它本質,還是幾個 CRUD 拼起來的。

權衡層:為什麼這樣設計?

你可能會問:既然萬變不離其宗,為什麼每個功能開發起來還那麼麻煩?

因為魔鬼藏在細節裡——具體到每個功能,工程師要思考的東西完全不同:

  • 點贊:考慮"高併發"——熱門微博一秒幾萬個贊,數據庫能扛得住嗎?通常要用計數器緩存和異步寫入。
  • 評論:考慮"內容安全"——惡意刷屏、辱罵、廣告怎麼辦?需要接入敏感詞檢測和限流。
  • 登錄:考慮"賬號安全"——密碼不能明文存(要 hash + salt),要防暴力破解、防撞庫,可能還要短信驗證碼或人機驗證。
  • 下單:考慮"錢的準確性"——庫存超賣、重複扣款、訂單錯亂都是災難,一切都要有回滾方案。
所以,程序員的功力,不在於會寫 CRUD——CRUD 誰都會寫。
功力在於:知道"這個場景下,需要額外考慮什麼"。

這也是為什麼"新手寫一個下單接口"和"資深工程師寫一個下單接口",代碼可能差 10 倍的行數——因為後者考慮了 10 倍的失敗場景。

✋ 動手試試

試試看:找出你熟悉 App 裡的"CRUD 模式"

隨便打開一個 App(微信、抖音、B 站……),挑一個你常用的功能,試著回答:

  • 它對應哪個表?(users? posts? follows?)
  • 它是在 Create、Read、Update 還是 Delete?
  • 它需要認證嗎?
  • 它需要保證冪等嗎?

比如:

  • 關注一個人 = Create follows 記錄 (user_id, target_id)
  • 取關 = Delete 同一條記錄
  • 刷推薦流 = Read 複雜的排序 + 分頁
  • 發朋友圈 = Create moments 記錄

做幾次這個練習,你就會有一種"看穿"App 的感覺。

👑 大帝視角:這如何塑造現實?

產品的"新功能",大多是老磚塊的新排列

你聽過"某某 App 上線了一個新功能",覺得很酷、很創新——但從工程師視角看, 大多數所謂"新功能"其實都是已經存在的原語的重新拼裝:

• 微博的"轉發" = 特殊類型的 Create
• 抖音的"收藏" = 類似點讚的 Create+Delete
• 淘寶的"購物車" = 用戶級別的臨時 Create,提交時批量轉成訂單
• 微信的"朋友圈" = Create post + 複雜的可見性(授權)控制
• 拼多多的"砍一刀" = Create + 狀態機 + 通知

真正的創新,不在"磚塊本身",而在"磚塊的組合方式"。

這也是為什麼優秀的產品經理和工程師,總是先問"這個功能能不能用現有的能力拼出來?"——因為拼裝的成本遠低於發明。

當你能識別出磚塊的組合模式,你就能從"用戶"躍升為"設計者"。 你會看到每一個流行的產品背後,都是一套精妙的"CRUD + 認證 + 業務規則"的編排。

這就是互聯網世界的秘密:它比看起來簡單得多,又比看起來精妙得多。

✨ 回到問題

所以,註冊、登錄、評論、點贊、下單……本質上是怎麼實現的?

它們幾乎都是 CRUD(創建、讀取、更新、刪除)+ 認證(你是誰)+ 授權(你能做啥)的組合。 只不過"下單"這類涉及錢和狀態的功能,還需要加上冪等性、事務、一致性等保命機制。

一旦你掌握了這套"磚塊清單",你會發現——世界上再複雜的產品,拆開來看,都是這些基礎塊的拼裝。 這種"看穿一切"的能力,是通往"造產品的人"的第一張車票。
