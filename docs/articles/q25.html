为什么大型网站总是在做监控、日志、链路追踪和故障演练？

看不见的系统 = 失控的系统；故障演练是给系统打疫苗

🤔 小白视角：这个问题为什么重要？

你可能听过程序员这样说："今天不上线，我们要压测。""周末做一次全链路故障演练。""这个 bug 我们看链路 traceId 排查。" 外行听起来像天书，但这些其实是大厂运转的"心跳"。

在 100 台机器、几千个服务的系统里，出了问题，你怎么知道是哪出问题？靠猜？靠命？ 答案是——大公司花了海量精力，就为了做一件事：让系统"看得见"。

核心观点：

看不见的系统，等于失控的系统。
你如果不能"观察到"系统的状态，你就没法维护它。
你如果没有"预演过"故障，它真来了你就是瞎子摸象。

🧩 拆解：把大问题拆成小问题

  1. 系统里到底有什么东西"看不见"？
  2. 监控、日志、追踪——到底有什么区别？
  3. 一次故障到底怎么排查？
  4. 为什么要"故意搞坏"自己的系统？

🎯 一层一层看

用户层：只看结果

用户对可观测性的感知是：什么都感觉不到，但结果就是"这家的服务真稳"。

  • 某天 10 点开始，抖音开屏偶尔白屏——你不会看到，但工程师的告警已经响了 100 次
  • 某个地方支付有延迟——工程师从链路追踪看到"支付 → 风控"那一步 P99 从 100ms 涨到了 2000ms
  • 某次微博服务器出问题——热搜可能"扛住"了，因为演练过 47 次类似场景

实现层：开始理解构造

最原始的"观察"就是——print。

def buy(item_id): print(f"[INFO] user buying item {item_id}") try: result = do_buy(item_id) print(f"[INFO] success: {result}") except Exception as e: print(f"[ERROR] failed: {e}")

这就是日志（Log）最朴素的样子。 但当你有 1000 台机器、每台 QPS 上万时，几十亿行日志散落各处—— 你怎么知道"哪一行是问题？"、"哪一个用户的请求走过哪些机器？"、"这一秒系统整体是什么状态？"

于是，可观测性演化出了三个不同"维度"：

系统层：看到完整链路

业界公认的可观测性三支柱（Three Pillars of Observability）：

【Metrics 指标】
→ 时序数字，回答"现状"
→ 例：QPS、CPU、错误率、P99 延迟
→ 工具：Prometheus + Grafana

【Logs 日志】
→ 结构化文本，回答"发生了什么"
→ 例：某个请求打印的详细信息、报错堆栈
→ 工具：ELK（Elasticsearch + Logstash + Kibana）、Loki

【Traces 链路追踪】
→ 一次请求的全流程，回答"跨服务的问题在哪一段"
→ 例：一个下单请求：网关 3ms → 用户 5ms → 库存 200ms(⚠️) → 支付 20ms
→ 工具：Jaeger、SkyWalking、OpenTelemetry

三者是互补的，不是替代关系：

Metrics（指标）

看整体健康度：CPU 是不是 100%？错误率有没有涨？
特点：轻量、能长期存、适合告警。
缺点：只能告诉你"有问题"，不告诉你"为什么"。

Logs（日志）

看细节：哪一行代码报错？堆栈是什么？
特点：信息最全、能查最深。
缺点：量太大、查询贵、跨服务时难串起来。

Traces（追踪）

看路径：一次请求经过了 20 个服务，哪一段慢了？
特点：跨服务、跨机器可视化。
关键：需要traceId 贯穿全链路。

Events / Alerts

看变化：什么时候发布过？什么时候扩容过？
把"人为动作"和"系统变化"关联起来，是排查故障的第 4 支柱。

真实排查案例：某天 P99 延迟从 100ms 涨到 800ms。

  1. 先看 Metrics——发现只有支付服务的延迟涨了
  2. 再看 Traces——发现是支付服务里"调用风控"那一步慢
  3. 再看 Logs——找到风控服务的报错："connection pool exhausted"
  4. 关联 Events——发现半小时前风控服务发布了新版本
  5. 结论：新版本连接池配置错了，回滚

这就是一次"从告警到根因"的完整闭环——没有可观测性，这半小时你根本查不出来。

权衡层：为什么这样设计？

你可能会问：既然日志这么好，为啥不"啥都记下来"？——因为代价惊人。

核心权衡：
观察力 ↔ 成本 & 性能
记得越细越全，存储成本越高、系统性能越差。
真实系统会做采样——只记录 1% 的请求详情。
  • Metrics 是"预聚合"：不存原始数据，只存"每秒的 QPS 数值"。便宜、快。
  • Logs 需要采样和轮转：INFO 保留 7 天，DEBUG 只保留几小时，超时自动删除。
  • Traces 需要头部采样：不能每个请求都追踪，通常只追 1%~10%，但"错误请求"和"慢请求"永远采。

💥 故障演练：给系统打疫苗

做完了监控、日志、追踪，还有一件"变态"的事：故障演练（Chaos Engineering）——主动往自己的系统里注入故障。

周四下午 3 点：

运维工程师："今天演练开始。"
→ 随机杀掉 5% 的机器
→ 让某个可用区断网 3 分钟
→ 让数据库延迟涨 500ms
→ 让缓存击穿 10%

观察：
· 告警响了吗？
· 有没有自动扩容？
· 用户端有没有报错？
· 恢复用了多久？

这个方法论最早由 Netflix 提出，他们的著名工具叫 Chaos Monkey——真的会在生产环境随机搞破坏。 你可能觉得疯了，但他们的逻辑是：

"故障总会发生的。
与其等到最坏那天才发现自己没准备好，
不如现在主动制造小故障，看看系统能不能扛住。"

这就是"给系统打疫苗"的思想——用小剂量、可控的故障，让系统产生对故障的免疫力。 阿里叫"红蓝对抗"、字节叫"混沌工程"、腾讯叫"故障演习"——名字不同，本质相同。

常见误区："监控告警越多越好"。
告警一多，就没人看了——这叫"告警疲劳"。真正好的监控是：只在需要人工介入时才响，能自愈的问题让系统自己修。 比如 P99 抖一下不用响，抖 5 分钟才响；单机 CPU 100% 不用响，整个集群平均 80% 才响。

✋ 动手试试

给你自己的项目加一个 traceId

在任意一个 Web 应用里试试：
1. 请求进来时生成一个 UUID，叫 traceId。
2. 把它塞到日志的每一行前面：[trace=abc123] user login。
3. 传给下游服务（用 HTTP Header X-Trace-Id）。
4. 下游也把这个 traceId 打到自己的日志里。

然后，当某个用户报"这次操作有问题"时，你只需要问他要那次请求的 traceId， 就能在 N 个服务的日志里搜出他这一次请求的完整路径—— 这就是链路追踪的雏形。 一旦体会过，你就再也回不去"没有 traceId"的日志时代了。

👑 大帝视角：这如何塑造现实？

看不见的系统 = 失控的系统

一个大道至简的真理：你无法管理你无法测量的东西。

这句话不只适用于系统，也适用于——

  • 公司管理：没有仪表盘的 CEO，就是在盲开飞机。KPI、财报、月度复盘——都是"公司这个系统"的监控。
  • 个人成长：没有"复盘 + 记录 + 反思"的人，永远原地打转。所谓"日志"，其实就是你人生的可观测性。
  • 国家治理：普查、统计、审计——都是"社会这个系统"的 metrics 和 logs。数据造假，等于系统瞎眼。

而"故障演练"更是深刻——它的哲学是"承认自己会出错"。

一个真正强大的系统，不是"从不出问题"的系统，而是"总在故意找自己麻烦"的系统。

· 消防演习：给城市打疫苗
· 军事演习：给国家打疫苗
· 应急预案：给组织打疫苗
· 复盘会：给团队打疫苗

凡是伟大的、能穿越周期的系统，都在做一件事：主动地、廉价地失败，来避免真实的、昂贵的失败。

✨ 回到问题

所以，为什么大型网站总是在做监控、日志、链路追踪和故障演练？

因为系统一旦复杂到某个程度，"能不能看见"比"写没写对"更重要。 Metrics 让你看到"发生了什么"、Logs 让你看到"细节是什么"、Traces 让你看到"路径怎么走的"，而演练让你在"真实故障来临前"就已经准备好了应对方案。

成熟系统的秘密不是"从不出错"，
而是"出错时你早就演练过 100 遍"。

这也是为什么工程师最贵的能力，从来不是"写代码"，
而是"在系统着火时，5 分钟内定位问题、10 分钟内恢复服务"。
