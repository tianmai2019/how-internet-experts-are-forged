注册、登录、评论、点赞、下单……本质上是怎么实现的?

互联网世界里,几乎所有功能都是"老砖块的新排列"

🤔 小白视角:这个问题为什么重要?

你在淘宝下单、在微博点赞、在小红书评论、在知乎登录……表面上看,这些是五种完全不同的功能。 但如果告诉你——它们背后其实是同一套东西——你会不会有点惊讶?

这个问题重要,是因为一旦你识别出这套"底层砖块",你会发现: 所谓"新产品的功能",大多都是老砖块的重新排列。 这种"看穿"的能力,是从"用产品的人"变成"造产品的人"的分水岭。

核心洞察:

所有这些功能,归纳起来只有四种操作:
Create(创建)、Read(读取)、Update(更新)、Delete(删除)
简称 CRUD——加上"知道你是谁"(认证)和"知道你能干什么"(授权),几乎能拼出整个互联网。

🧩 拆解:把大问题拆成小问题

  1. 不同功能之间,共同的抽象是什么?
  2. "你是谁"这件事,系统怎么记住?
  3. "点赞"和"评论"看起来不一样,底层为啥说是一回事?
  4. 下单为什么比点赞"重"很多?"重"在哪儿?

🎯 一层一层看

用户层:只看结果

你觉得:

  • 注册——填个手机号,创建了账号
  • 登录——输入密码,进入了世界
  • 评论——写点字,发出去
  • 点赞——按一下,变红
  • 下单——选商品、付款、等发货

看起来是五件不同的事。但工程师眼里……

实现层:开始理解构造

我们把这五个功能"翻译"成 CRUD 操作,你会看到魔法:

📝 注册

Create 一条 users 记录

INSERT INTO users(phone, password_hash) VALUES(?, ?)

🔑 登录

Read users 表 + 发一个 token

SELECT id FROM users WHERE phone=? AND password_hash=?

💬 评论

Create 一条 comments 记录

INSERT INTO comments(user_id, post_id, text) VALUES(?, ?, ?)

❤️ 点赞

Create 一条 likes 记录(取消赞就 Delete)

INSERT INTO likes(user_id, post_id) VALUES(?, ?)

🛒 下单

Create orders + Update inventory + Create payment……

比较复杂,但每一步都是 CRUD。

💡 结论

互联网的绝大多数功能 = CRUD 的组合 + 认证 + 一些业务规则

惊不惊喜?让我们看得更深一点——先看"登录"到底是怎么"记住你"的。

"你是谁"这件事:session vs token

HTTP 是一个无状态协议——服务器每次收到你的请求,都像失忆了一样,不知道你是谁。 所以,系统必须想办法在每次请求时"证明你是谁"。目前有两种主流做法:

🎟️ Session(会话)

登录后,服务器生成一个 session id,存在它自己的数据库里。

下发给你一个 cookie。每次请求,浏览器带上 cookie,服务器去查。

就像"寄存牌"——牌子在你手里,东西在店里。

🪪 Token(令牌,JWT)

登录后,服务器签发一个加密串(里面藏着"你是 user_123, 有效到 xxx"),交给你。

每次请求带上,服务器验签就行,不需要查库。

就像"身份证"——真伪一看就知道。

前端代码里,登录后通常长这样:

// 登录成功后,把 token 存起来 const res = await fetch('/api/login', { method: 'POST', body: JSON.stringify({ phone, password }) }); const { token } = await res.json(); localStorage.setItem('token', token); // 之后所有请求都自动带上 await fetch('/api/comments', { headers: { 'Authorization': `Bearer ${token}` }, method: 'POST', body: JSON.stringify({ postId: 42, text: '好文!' }) });

系统层:看到完整链路

我们放大一次"下单"——因为它最能体现工程师如何把 CRUD 组合成"复杂功能":

① 认证 · 你是谁?
↓
② 校验 · 商品还在吗?
↓
③ 扣库存 · Update inventory
↓
④ 创建订单 · Create orders
↓
⑤ 发起支付 · 调用第三方
↓
⑥ 更新订单状态 · Update
↓
⑦ 通知商家发货

重点来了:下单和点赞的本质区别是——

幂等性 · 事务性 · 一致性

点赞:同一个人点两次和一次没差别(去重就行) → 幂等
下单:你重复点"支付",绝不能收两次钱 → 必须严格幂等
下单:扣库存和创建订单必须同时成功或同时失败 → 事务
下单:数据库、库存、支付、商家四个系统,数据要"最终对得上" → 一致性

所以一个"下单"接口,可能有几十甚至几百行代码,内部小心翼翼地处理各种失败场景。 但它本质,还是几个 CRUD 拼起来的。

权衡层:为什么这样设计?

你可能会问:既然万变不离其宗,为什么每个功能开发起来还那么麻烦?

因为魔鬼藏在细节里——具体到每个功能,工程师要思考的东西完全不同:

  • 点赞:考虑"高并发"——热门微博一秒几万个赞,数据库能扛得住吗?通常要用计数器缓存和异步写入。
  • 评论:考虑"内容安全"——恶意刷屏、辱骂、广告怎么办?需要接入敏感词检测和限流。
  • 登录:考虑"账号安全"——密码不能明文存(要 hash + salt),要防暴力破解、防撞库,可能还要短信验证码或人机验证。
  • 下单:考虑"钱的准确性"——库存超卖、重复扣款、订单错乱都是灾难,一切都要有回滚方案。
所以,程序员的功力,不在于会写 CRUD——CRUD 谁都会写。
功力在于:知道"这个场景下,需要额外考虑什么"。

这也是为什么"新手写一个下单接口"和"资深工程师写一个下单接口",代码可能差 10 倍的行数——因为后者考虑了 10 倍的失败场景。

✋ 动手试试

试试看:找出你熟悉 App 里的"CRUD 模式"

随便打开一个 App(微信、抖音、B 站……),挑一个你常用的功能,试着回答:

  • 它对应哪个表?(users? posts? follows?)
  • 它是在 Create、Read、Update 还是 Delete?
  • 它需要认证吗?
  • 它需要保证幂等吗?

比如:

  • 关注一个人 = Create follows 记录 (user_id, target_id)
  • 取关 = Delete 同一条记录
  • 刷推荐流 = Read 复杂的排序 + 分页
  • 发朋友圈 = Create moments 记录

做几次这个练习,你就会有一种"看穿"App 的感觉。

👑 大帝视角:这如何塑造现实?

产品的"新功能",大多是老砖块的新排列

你听过"某某 App 上线了一个新功能",觉得很酷、很创新——但从工程师视角看, 大多数所谓"新功能"其实都是已经存在的原语的重新拼装:

• 微博的"转发" = 特殊类型的 Create
• 抖音的"收藏" = 类似点赞的 Create+Delete
• 淘宝的"购物车" = 用户级别的临时 Create,提交时批量转成订单
• 微信的"朋友圈" = Create post + 复杂的可见性(授权)控制
• 拼多多的"砍一刀" = Create + 状态机 + 通知

真正的创新,不在"砖块本身",而在"砖块的组合方式"。

这也是为什么优秀的产品经理和工程师,总是先问"这个功能能不能用现有的能力拼出来?"——因为拼装的成本远低于发明。

当你能识别出砖块的组合模式,你就能从"用户"跃升为"设计者"。 你会看到每一个流行的产品背后,都是一套精妙的"CRUD + 认证 + 业务规则"的编排。

这就是互联网世界的秘密:它比看起来简单得多,又比看起来精妙得多。

✨ 回到问题

所以,注册、登录、评论、点赞、下单……本质上是怎么实现的?

它们几乎都是 CRUD(创建、读取、更新、删除)+ 认证(你是谁)+ 授权(你能做啥)的组合。 只不过"下单"这类涉及钱和状态的功能,还需要加上幂等性、事务、一致性等保命机制。

一旦你掌握了这套"砖块清单",你会发现——世界上再复杂的产品,拆开来看,都是这些基础块的拼装。 这种"看穿一切"的能力,是通往"造产品的人"的第一张车票。
