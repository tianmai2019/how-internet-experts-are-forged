为什么访问量一大，原本正常的系统就会开始超时、报错甚至崩溃？

稳定性，是"日常假设"在压力下的一次次崩塌

🤔 小白视角：这个问题为什么重要？

每年双 11 零点，你几乎能看到"淘宝崩了"上热搜；春运抢票时，12306 一度成为程序员集体嘲讽对象；世界杯的时候，直播平台一起变卡；某个明星突然官宣结婚，微博就挂了。

奇怪的是：这些系统平时都跑得好好的。凭什么用户一多，就翻车？

因为系统的"正常"，其实是一堆假设——只是这些假设平时没被拆穿。

流量一大，所有假设一起崩塌。这就是所谓的雪崩。

🧩 拆解：把大问题拆成小问题

  1. 并发是什么？为什么"很多人同时来"和"一个人来 100 次"完全不同？
  2. 资源是有限的：连接、线程、内存、数据库连接池，都有天花板。
  3. 慢会传染：为什么一个环节变慢，会拖垮整个系统？
  4. 雪崩效应：崩溃是怎么从"局部"扩散到"全局"的？

🎯 一层一层看

用户层：只看结果

用户会看到：转圈、白屏、"网络不稳定，请稍后再试"、"服务器繁忙"、直接 502 页面。

用户不会知道：这背后是几百万人同时挤进来，把某个原本能容纳 1 万连接的组件挤爆了。

实现层：开始理解构造

我们平时写的服务大概长这样：

// 一个再普通不过的接口 app.get('/order/:id', async (req, res) => { const order = await db.query( 'SELECT * FROM orders WHERE id = ?', [req.params.id] ) res.json(order) })

在开发环境、在测试的时候，它一切正常。你 QPS 打到 10、100、1000，也许都还好。但当 QPS 冲到 10 万，问题一个接一个爆出来：

  • 数据库连接池只有 100 个，第 101 个请求开始排队。
  • 每个 SQL 平时 10ms，压力大了变成 500ms，因为磁盘 IO 拥挤 / 锁等待。
  • Node 的事件循环、Java 的线程池，也在被"占着不放"的慢请求逐渐吃满。
  • 调用方等不到响应，超时，重试，把请求量又放大一倍。

系统层：看到完整链路

单点看不出雪崩，我们退一步看整条链路：

[ 用户流量 ×100 ] ↓ 接入层 (Nginx / LB) ← 连接数暴涨，可能耗尽 FD ↓ API 网关 / 应用服务 ← 线程被慢调用占满 ↓ 下游微服务 A、B、C ← 任何一个变慢都往回传染 ↓ 数据库 / Redis ← 连接池打满，锁等待激增 ↓ [ 客户端超时 → 重试 ] ────→ 再次涌回入口（正反馈！）

注意最后那条虚线——客户端在重试。这是很多雪崩最致命的加速器：一次慢响应引发一次重试，把原本 10 万 QPS 变成 20 万、40 万，系统更慢，更多重试，直到彻底躺平。

所以雪崩的公式大致是：

雪崩 = 慢 + 有限资源 + 无节制的重试 + 无边界的调用链

这四个因素单独都不致命，凑在一起就是灾难。

权衡层：为什么这样设计？

你可能会问：既然会崩，为什么不一开始就设计成"永远不崩"？

因为"扛得住高并发"很贵：

方案 A：按峰值备容

永远保留双 11 级别的机器数，绝大部分时间闲置，成本极高。

方案 B：按平均备容 + 弹性扩容

成本低，但扩容需要时间；突发流量还没扩上来，就已经打崩了。

方案 C：加限流 / 排队 / 降级

牺牲一部分体验（排队、少功能）换整体不崩，工程上最实用。

方案 D：全异步 + 消息队列

吞下所有请求慢慢消化，但对实时性要求高的场景不适用。

所有大公司都在做的，是一个组合拳：提前扩容 + 限流 + 队列削峰 + 熔断降级，这些正是 Q17 里的"六件套"。

常见误区：以为"系统崩溃 = 硬件不够"。事实上大多数崩溃发生时，CPU 使用率并不高——真正打满的往往是连接数、线程数、连接池、锁这些"资源计数"。加机器有时反而无效，因为瓶颈根本不在算力。

✋ 动手试试

亲手压一个小服务看看

在本机跑一个最简单的 Node/Python 服务，加一句 sleep(500ms) 模拟慢查询。然后用压测工具打它：

ab -n 10000 -c 500 http://localhost:3000/hello # 或者用 hey / wrk / k6

观察：当并发 -c 从 10 提到 500，你的 P99 延迟、错误率、超时率会怎么变化？打开 ss -s 看看 TCP 连接堆积。你会亲眼看到——同样的代码，负载不同，"结果"完全不同。

👑 大帝视角：这如何塑造现实？

稳定性，是「假设」在压力下的诚实性检验

平时跑得好好的系统，其实建立在无数条隐含假设上： "用户不会同时都来"、"数据库连接够用"、"下游不会挂"、"网络不会抖"、"没人会疯狂重试"。

大流量的意义，是把这些假设一次性摊在阳光下。哪条假设不成立，系统就在哪里裂开一道口子。所以大厂的"双 11 大促"，本质上不只是卖货——那是每年一次组织级的假设审计。

往大了看，这也是"扩张"的通用规律：一家小公司变成大公司，一个小国变成大国，都会经历这一刻——原本运作良好的规矩，被规模一压就露馅。稳定性工程，本质上是把假设写下来、量化、加护栏。

✨ 回到问题

所以，为什么流量一大就崩？

因为"正常"是一种低负载下才成立的错觉。

资源是有限的，慢会传染，重试会放大，链路会连坐。
当所有这些一起发生，就是雪崩。

所以真正牛的系统，不是永远不慢，而是慢的时候不会全挂。
