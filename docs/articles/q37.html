为什么组织结构会反过来影响系统架构？

康威定律：你画的架构图，最后长成了你的组织架构图

🤔 小白视角：这个问题为什么重要？

你可能听过一个"迷"：为什么很多大公司的产品，看起来功能是拼在一起的？ 为什么淘宝和支付宝这么像但又分裂？为什么一个 App 里，不同 tab 的设计风格完全不同？

你以为是"设计师能力不齐"或"产品经理没眼光"。其实背后有一条铁律：

康威定律（Conway's Law, 1968）：

"任何组织设计出的系统，最终都会反映这个组织的沟通结构。"

→ 3 个团队做浏览器，会做出 3 个模块拼起来的浏览器。
→ 一个团队做的，就是一个 monolith。

换句话说：你的组织什么样，你的代码就什么样。 这是软件工程里最"隐形"、也最不可抗拒的力量。

🧩 拆解：把大问题拆成小问题

  1. 康威定律到底说的什么？
  2. 为什么组织结构会决定系统结构？
  3. 反过来，能不能"改组织"来"改架构"？（逆康威）
  4. Amazon、Netflix、字节都在这个定律上做了什么？

🎯 一层一层看

用户层：只看结果

用户会说："这个 App 有些地方好用，有些地方特别割裂。" "登录一下要跳三个页面。""搜索出来的商品和购物车看着完全不是一个团队做的。"

这些"割裂感"，往往就是组织墙的投影。

实现层：开始理解构造

假设有 3 个团队要合作做一个 App：

// 三个团队各自的边界 Team A: 用户模块 → 一个 UserService Team B: 商品模块 → 一个 ProductService Team C: 支付模块 → 一个 PaymentService // 结果：架构自然分成三块 // 因为跨团队沟通有成本，所以 API 边界总是在团队边界上 // 如果 Team A 和 Team B 有矛盾？ // —— 会出现一个"翻译层"来解耦 // —— 这个翻译层，就是"人际关系"在代码里的实体化

这不是理论——它每天都在发生。你的 team 里三个人不说话，代码里就会多一个中间层。

系统层：看到完整链路

Amazon 是把这个定律"逆向"用得最成功的公司。看这条链路：

Jeff Bezos 的"两个披萨团队"规则（2002 年） ↓ 每个团队小到"两个披萨能吃饱"（6-10 人） ↓ 每个团队独立、有 KPI、有 API 边界 ↓ 团队之间必须通过 API 通信，不许"跳过 API" ↓ 组织成了微服务的形状 ↓ 系统架构自然成了微服务架构 ↓ 这些内部 API 变成了 AWS

这就是逆康威定律（Inverse Conway Maneuver）： 想要什么样的系统架构，就先把组织改成那个样子。

权衡层：为什么这样设计？

微服务是好的？大 monolith 是坏的？不一定——每个选择对应不同的组织现实：

Monolith（单体）

适合小团队（< 30 人）。所有人共享一个代码库，沟通成本低，迭代快。

Microservice（微服务）

适合大组织。让每个团队自治，用 API 隔离沟通复杂度——但代价是运维和一致性。

Modular Monolith

中间态。代码物理上一起，但逻辑上分层。适合"想微服务但组织还没到"的团队。

Distributed Monolith

最糟的一种。看着是微服务，实际耦合还在。往往是"没改组织就先改架构"的结果。

架构选择的第一问，从来不是"技术上哪个好"，而是"我的组织长什么样"。

✋ 动手试试

🔍 观察实验：画一次"组织架构 vs 系统架构"

找一款你熟悉的产品（比如淘宝、微信、抖音），试着回答：

  1. 把它的主要模块画出来（推荐、搜索、聊天、支付、直播……）；
  2. 猜猜每个模块背后是几个团队；
  3. 观察哪些模块"衔接得顺"（可能是同一个 BU）？
  4. 观察哪些模块"衔接得别扭"（可能是不同 BU 拼的）？

如果你在公司里工作过，回头看你们的产品，你会发现每一个别扭的地方，都对应一堵组织墙。

👑 大帝视角：这如何塑造现实？

系统架构 = 组织架构在代码里的投影

康威定律的深层含义是：软件不是"设计出来的"，是"生长出来的"。 它跟随组织的形状生长，跟随人的沟通路径生长，跟随权力关系生长。

这解释了很多"技术之谜"：

  • 为什么 Google 的产品经常"启动又下架"？——因为组织结构频繁重组；
  • 为什么大公司的技术栈总是分裂？——因为不同 BU 独立选型；
  • 为什么开源项目常常演化成"许多小模块的联邦"？——因为贡献者是分布式的；
  • 为什么创业公司做的 App 总是"一致感"更强？——因为团队小、沟通密、边界少。

大帝视角看到的更深一层是：技术架构和社会结构，是同一件事的两面。 你如何组织人，就在如何组织信息；你如何组织信息，就在决定这个系统能长成什么样。

这也是为什么真正好的 CTO，同时也是好的组织设计师。
修代码的人，其实是在修人和人之间的关系。

✨ 回到问题

所以，为什么组织结构会反过来影响系统架构？

答案是：因为软件是人写的，而人的沟通结构决定了代码的耦合结构。 你不能画一张漂亮的架构图，然后期望它在一个乱糟糟的组织里"实现出来"—— 它最终会长成组织真实的样子。

大帝视角的觉醒：

下次你看到一个"难看的系统"，先别怪工程师。
问一问：做这个系统的组织，长什么样？
答案往往就在那里。
