数据库到底在存什么?

世界被建模成表格,才能被系统"看见"

🤔 小白视角:这个问题为什么重要?

你的支付宝余额、你的微信好友、你在淘宝买过的每一件东西、你去年 3 月 12 号发的那条朋友圈——它们都存在某个地方。 这个地方叫"数据库"。

但数据库到底长什么样?是一个巨大的文件吗?是一堆 Excel 表格吗? 更重要的是:什么东西能被存进去,什么不能?

核心洞察:

数据库不存"现实",它存的是被模型化过的现实——
你必须先决定"这个东西有哪几个属性、和其他东西怎么关联",
才能把它塞进数据库。

没被建模的东西,系统就"看不见"。

这个问题重要,不是因为你要学 SQL——而是因为一旦你理解了"数据库如何看世界",你就理解了产品经理为什么天天在争"这个字段要不要加"、"这两个东西是不是同一类"。

🧩 拆解:把大问题拆成小问题

  1. 数据库长什么样?
  2. 为什么"表格"这种形式能存下现实?
  3. 索引、事务、schema 这些术语在说啥?
  4. 为什么会有"关系型"和"非关系型"两派?

🎯 一层一层看

用户层:只看结果

你打开美团,看到你上个月点的那单奶茶——"太后奶盖抹茶,加芋圆,不加糖"。 你觉得,美团"记得"你买过什么。

但美团怎么"记得"?它不是像人一样有记忆——它有一张表,叫 orders,里面有一行,大致长这样:

order_id | user_id | shop_id | items | price | status | created_at ---------+---------+---------+--------------------------------+-------+---------+--------------------- 9382174 | 8827 | 501 | 太后奶盖抹茶(加芋圆,不加糖) | 22.5 | 已完成 | 2024-05-13 14:22:41

这一行,就是你的那杯奶茶被数据库"记住"的方式。它不是你的记忆的复制,它是一个"被格式化的事实"。

实现层:开始理解构造

最常见的一类数据库,叫关系型数据库(MySQL、PostgreSQL、SQL Server……)。 它把世界描述成一堆"表格",每个表格有行(row)和列(column):

一个最简单的博客系统,需要什么表?
-- 用户表:每个用户一行 CREATE TABLE users ( id BIGINT PRIMARY KEY, phone VARCHAR(20) UNIQUE, nickname VARCHAR(50), created_at TIMESTAMP ); -- 帖子表:每个帖子一行 CREATE TABLE posts ( id BIGINT PRIMARY KEY, author_id BIGINT REFERENCES users(id), -- 谁写的 title VARCHAR(200), content TEXT, created_at TIMESTAMP ); -- 评论表:每条评论一行 CREATE TABLE comments ( id BIGINT PRIMARY KEY, post_id BIGINT REFERENCES posts(id), -- 评论哪条 user_id BIGINT REFERENCES users(id), -- 谁评的 text TEXT, created_at TIMESTAMP );

注意那几个 REFERENCES——这是"关系"的核心。 comments 表的每一行,通过 post_id 和 user_id 指向另外两张表的具体一行。 所以叫"关系型"——表和表之间有关系。

有了表,你就可以"问问题":

-- 找出用户 8827 昨天写的所有帖子 SELECT id, title, created_at FROM posts WHERE author_id = 8827 AND created_at >= '2024-05-12' AND created_at < '2024-05-13'; -- 找出这条帖子下所有评论,包括评论者的昵称 SELECT c.text, u.nickname, c.created_at FROM comments c JOIN users u ON u.id = c.user_id WHERE c.post_id = 42 ORDER BY c.created_at DESC;

SQL 就是"跟数据库对话的语言"。它读起来像英语,写起来是"我想要什么",不是"你怎么找"。

系统层:看到完整链路

如果数据库只是"存表格",几十年下来没什么好研究的。 但数据库真正难的地方,是要在"快、对、可靠"之间平衡。为此,它引入了几个关键概念:

📇 索引(Index)

就像书的目录。没有目录时,查一个词要翻整本书;有了目录,秒定位。

代价:目录本身要占空间,而且写数据时得同时更新目录。

🔒 事务(Transaction)

一组操作要么全部成功,要么全部失败。

转账时,"从我账户扣 100"和"给对方账户加 100",必须同生共死——不然钱就凭空消失或凭空多出。

📐 Schema(模式)

数据库的"设计蓝图"——有几张表、每张表有哪些字段、字段是什么类型。

产品迭代时,加字段、改类型都叫"schema 变更",搞不好会宕机。

♻️ 事务的 ACID

Atomicity 原子性、Consistency 一致性、Isolation 隔离性、Durability 持久性——数据库为"钱"和"账"提供的安全保证。

一次数据库读写,幕后发生了什么?
① SQL 到达
↓ 解析 + 优化
② 生成执行计划
↓ 决定用哪个索引
③ 读磁盘/内存页
↓ 汇总结果
④ 返回给应用

数据库不会去"遍历硬盘上的每一个字节"——它维护着一套精心设计的B+ 树、哈希表、日志文件, 让"查一条数据"通常只需要几次磁盘 I/O,毫秒级完成。

权衡层:关系型 vs NoSQL,为什么会分家?

几十年来关系型数据库统治天下,但 2010 年前后,一批"叛军"出现了——MongoDB、Redis、Cassandra、Elasticsearch…… 它们统称 NoSQL(Not Only SQL)。

🏛️ 关系型(MySQL, PostgreSQL)

结构严谨,支持复杂查询和事务。

适合:钱、账、订单、用户关系——一切"错不得"的场景。

短板:海量数据难以水平扩展。

🚀 NoSQL(MongoDB, Redis, Cassandra)

形式灵活,牺牲一些一致性换取巨大的性能和扩展性。

适合:缓存、日志、社交动态、搜索——一切"多、快、变得快"的场景。

短板:复杂事务和跨表查询较弱。

真实世界的大型系统,通常两派都用:

  • 你的账户余额、订单——放在 MySQL/PostgreSQL(要"对")
  • 你的动态流、推荐结果——放在 Redis/MongoDB(要"快")
  • 你的搜索关键词、日志——放在 Elasticsearch(要"能全文搜")
这也说明一件事:

"数据库"其实不是一种东西,而是一大类工具。
工程师的活儿,是在众多数据库里挑合适的组合,来匹配业务需求。

✋ 动手试试

试试看:5 分钟,写下你熟悉产品的"数据模型"

拿一张纸(或任何笔记 App),想一个你熟悉的产品——比如"微信"或"抖音"。
然后回答:如果你是它的工程师,你需要哪几张表?

以微信为例,你可能会写下:

  • users: id, phone, nickname, avatar_url
  • friends: user_id, friend_id, added_at (谁和谁是好友)
  • chats: id, type(单聊/群聊), created_at
  • messages: id, chat_id, sender_id, content, sent_at
  • moments: id, user_id, text, images, posted_at

做完这个练习,你会有一种奇妙的感觉:
一个 App,其实就是一堆表的集合。

👑 大帝视角:这如何塑造现实?

能被数据库表达的世界,才被系统"看见"

这是一个容易被忽略的深刻现实:

如果一件事情不能被建模成"表和字段",互联网系统就无法处理它。

你的性别是"男/女"?——因为一开始的表里,gender 字段只有两个枚举值。 今天很多平台开始加"其他""不愿透露""非二元",这不是社会突然进步了,而是数据库的 schema 被扩展了。

你的身份证只能是 18 位数字?你的名字不能超过 20 个字?你的家庭关系必须是"父/母/子/女"? 这些看似天经地义的"规则",本质都是某位工程师在定义表结构时下的决定。

数据库是"现实的过滤器"。它决定了什么被系统看到、什么被系统忽略、什么被系统强行归类。

每一次你在 App 里填一张表单,你都在把"活生生的自己"翻译成机器能理解的字段。 你的复杂被压缩,你的多面被单选,你的模糊被枚举——这就是"数字化生存"的代价。

这也是为什么每一次 schema 变更、每一次"字段新增",都可能是一场无声的社会讨论。

✨ 回到问题

所以,数据库到底在存什么?

它存的不是"世界",而是"被工程师建模过的世界"——一张张有严格结构的表格, 行是记录,列是属性,表与表之间通过关联表达关系。

这背后有一整套精妙的机器:索引让查找变快、事务保证一致、schema 约束数据形状。 关系型和 NoSQL 是不同侧重的两派,现代系统通常两派并用。

更深一层的真相:

当你以后打开任何一个 App,试着问自己:
"如果我是它的工程师,我会怎么设计它的表?"

你能想到几张表——你就理解了这个产品的几分。

至此,你已经走完了"程序员入门视角"的第一段旅程。恭喜你——从看世界的人,变成了能看穿世界结构的人。
